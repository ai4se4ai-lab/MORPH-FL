\title{MORPH-FL: Remembering Evidence, Forgetting Dialogue in LLM Fault Localization}
\author{Majid Babaei}
\maketitle
\begin{abstract}
Large language model (LLM) agents localize faults by proposing explanations, inspecting source code, and checking what those explanations predict. What they learn accumulates in a single dialogue, where facts established by checks sit beside conjectures and the reasoning that produced them. Keeping the dialogue carries early conjectures into every later step; discarding or summarizing it loses or blurs the facts. We argue that deciding what an investigation should forget is a modeling problem: observations, hypotheses, and dialogue differ in epistemic standing and should differ in lifetime. We present \tool{}, a model-driven approach that maintains a fault investigation as four linked runtime models of the reported behavior, the program structure, the competing fault hypotheses, and the probes, observations, and assessments that bear on them. Model operations ground LLM proposals in versioned source, assess observations against predictions, and project the models into every LLM request. Every request shows a small portfolio of hypotheses chosen for score and diversity rather than the current leader alone, because no localization score reliably identifies the correct explanation. When recent rounds yield no new observations while the investigation repeats its probes or its hypotheses converge, \tool{} resets the context: it clears the dialogue, keeps every observation and the cumulative budget, and discards the hypotheses outside the portfolio. We specify the metamodel, its invariants, and the reset policy, implement them for Python repositories, and define a controlled evaluation on SWE-bench Lite and Verified that isolates reset timing, hypothesis retention, and model-based context construction.
\end{abstract}
\begin{IEEEkeywords}
Fault localization, model-driven engineering, models at runtime, large language models, context management.
\end{IEEEkeywords}

\section{Introduction}\label{sec:intro}
A bug report describes where a failure becomes visible, not where it originates. Suppose a report states that a feature remains visible after the user disables it. The report's words point to rendering code, yet the fault may lie in a configuration function that silently replaces an explicit false value with a default. Localizing such a fault means connecting the symptom to candidate locations, proposing how each could produce the failure, and checking those proposals against the code.

Agents built on large language models (LLMs) now carry out this kind of investigation. AutoFL explores a repository with tools and explains its method-level predictions~\cite{autofl2024}. AgentFL divides the work into comprehension, navigation, and confirmation~\cite{agentfl2024}. Agentless and AutoCodeRover narrow the search before generating a repair~\cite{agentless2025,autocoderover2024}, and LocAgent and ARISE navigate repository graphs~\cite{locagent2025,arise2026}. In each system the next action depends on what the agent has learned so far, and most of that knowledge lives in the agent's dialogue.

A localization dialogue mixes three kinds of content. Some of it records facts that a check established, such as the presence of an expression in a file at a given revision. Some of it states conjectures: this function replaces false with a default. The rest is the reasoning that connected the two. As the dialogue grows, the mixture becomes harder to use. LLMs do not use long contexts uniformly~\cite{lostmiddle2024}. In a multi-role investigation, an early conjecture restated by several roles can read as corroboration although nothing new was observed, and LLMs struggle to correct their own reasoning without external feedback~\cite{selfcorrect2024}. Clearing the dialogue removes these influences, but it also discards the facts. The design question is therefore not how much history to keep. It is \emph{which parts of an investigation should survive a context reset}.

Existing context policies answer this question while treating the history as a single artifact. MemGPT pages messages between a bounded context and external storage and summarizes what it evicts~\cite{memgpt2024}. Reflexion carries verbal reflections from one trial to the next~\cite{reflexion2023}. Ledger renders the current execution state from a record of observed source, edits, and commands, alongside the interaction history~\cite{ledger2026}. Closest to our setting, recent work on automated discovery clears agent sessions and restarts the search from the best evaluated candidate~\cite{forgetting2026}. That strategy depends on an objective that scores candidates reliably. Fault localization offers no such oracle while the investigation is running: a hypothesis that leads by score may still be wrong, and restarting from it alone can lead the investigation back into the same line of reasoning.

Our premise is that observations, hypotheses, and dialogue deserve different lifetimes. An observation is a fact about a fixed revision and stays true however the investigation proceeds. A hypothesis is a conjecture and should compete with alternatives until the evidence separates them. The dialogue is a working medium that can be discarded once its results are recorded elsewhere. Model-driven engineering (MDE) offers a direct way to act on this premise. When the investigation state is a set of models conforming to a metamodel, each element can carry an explicit epistemic status, forgetting becomes an operation over model elements with a checkable preservation obligation, and each LLM request becomes a view derived from the models instead of a transcript of earlier requests.

We present \tool{}, a fault-localization approach built on this premise. \tool{} keeps four linked models outside the LLM dialogue: a behavior model of the report, a structure model of the source code, a hypothesis model of competing explanations, and an evidence model of probes, observations, and assessments. Investigator roles propose hypotheses together with probes that would check their predictions. Model operations ground each proposal in versioned source, run or reuse its probe, and assess the result. Every request shows a small portfolio of hypotheses selected for both score and diversity. A monitor watches for stagnation, that is, rounds that add no observation while the investigation repeats probes or its hypotheses converge. On stagnation, \tool{} clears all role dialogues, keeps every observation, and discards the hypotheses outside the portfolio; the next request is projected from what remains. In the configuration example, a reset keeps both observations and both competing explanations and drops the discussion in which they were debated.

We also define a controlled evaluation around three research questions. \textbf{RQ1} asks how accurately \tool{} ranks files and functions compared with other localization workflows. \textbf{RQ2} asks how model-based context construction, reset timing, and hypothesis retention affect investigation behavior. \textbf{RQ3} asks which accuracy--cost tradeoffs these policies produce. On SWE-bench Lite and Verified, the design compares \tool{} with continuous-context, periodic-reset, and evidence-only workflows, the last of which shows observations without hypotheses or dialogue, and with restricted adaptations of Agentless and RGFL. It adds component ablations and a track in which each investigation starts from a misleading lead.

This paper makes four contributions:
\begin{itemize}
\item A formulation of context management for LLM-based fault localization as a retention decision over observations, hypotheses, and dialogue, with the argument that, absent an oracle score, the investigation should keep a diverse hypothesis portfolio, in every request and across resets, rather than only the current leader.
\item An investigation metamodel with four linked models, explicit epistemic status, and four invariants---epistemic separation, source traceability, referential integrity, and observation preservation---that its operations maintain.
\item A stagnation-triggered reset policy that combines observation gain, probe repetition, hypothesis diversity, and remaining budget, prunes hypotheses by score and diversity, and rebuilds the context by projection rather than by summarization.
\item An open Python implementation and a controlled evaluation design that isolates reset timing, hypothesis retention, and model-based context construction, including investigations seeded with a misleading lead.
\end{itemize}

\section{Background and Motivating Example}\label{sec:background}
\subsection{Report-Based Fault Localization}\label{sec:problem}
The input to report-based fault localization is a bug report and a snapshot of the repository before the fix. The output is a ranked list of source locations for a developer to inspect. We consider two granularities: files, identified by repository-relative paths, and functions, identified by qualified names within those files. A ranking says where to look. An explanation additionally says how an operation could cause the reported failure.

Evidence about an explanation comes from checks of different strength. A source check establishes that a line contains some text. An abstract syntax tree (AST) query establishes that a file contains a syntactic structure. An execution procedure establishes what the program does for chosen inputs. We follow one convention throughout: a check \emph{supports} a hypothesis when the observed value equals the value its prediction expects, for example when a predicted expression is present in the inspected artifact. Support from a source or AST check is therefore a static fact; it does not show that the reported execution reached the code in question. The investigator sees the report, the pre-fix source, and the procedures it is allowed to run. It never sees the reference patch, which the evaluation uses only to derive target locations.

\subsection{Motivating Example}\label{sec:example}
Listing~\ref{lst:example} shows a constructed example that we use throughout the paper. A report states that setting \code{enabled} to false still displays a feature. The handler passes the normalized option to a rendering function, which is omitted. The fault is in \code{normalize}: the expression \code{options.get("enabled") or True} evaluates to true when the option is false. Line numbers are counted within each file, so the defaulting return is \code{config.py:2} and the handler's return is \code{handler.py:4}.
\begin{lstlisting}[float=t,language=Python,numbers=none,basicstyle=\ttfamily\scriptsize,frame=lines,framesep=3pt,xleftmargin=0pt,belowcaptionskip=6pt,caption={Constructed configuration fault in two Python files.},label={lst:example}]
# config.py
def normalize(options):
    return {"enabled": options.get("enabled") or True}

# handler.py
from config import normalize
def handle(options):
    config = normalize(options)
    return render(config["enabled"])
\end{lstlisting}

The report describes what is displayed, so an investigator may plausibly suspect the handler first, since it passes the option to the renderer. Two explanations then compete. The \emph{bypass} hypothesis claims that the handler renders the raw option instead of the normalized value; it predicts that the handler's return expression mentions \code{options}. The \emph{defaulting} hypothesis claims that \code{normalize} replaces an explicit false with a default; it predicts a return expression containing \code{or True}. Table~\ref{tab:example_checks} shows one AST check for each prediction. The first contradicts the bypass prediction, and the second supports the defaulting prediction. Neither check executes the program, so the defaulting explanation remains a hypothesis, now with structural support.

Now suppose the investigation stalls: later rounds re-propose the same checks and learn nothing new. Restarting with an empty context would force the investigator to rediscover both results. Restarting from the leading explanation alone would drop the bypass hypothesis together with the record that it was refuted, and a later round could propose the same idea again with nothing in its context to show that it had already failed. What the next round needs is the report, both observations, and both competing explanations, without the dialogue in which they were debated. Section~\ref{sec:approach} shows how \tool{} makes this selection precise.

\subsection{Models at Runtime}\label{sec:mde_background}
In MDE, a model represents selected aspects of a system in an explicit structure. A metamodel defines the admissible element types, attributes, and relationships, and transformations derive models or views from other models~\cite{mde2006}. Models need not be design-time artifacts. The models@run.time paradigm keeps a model of a running system and use it to drive the system's adaptation~\cite{modelsruntime2009}, much as the monitor--analyze--plan--execute loop of autonomic computing does~\cite{mapek2003}. \tool{} applies this idea to an investigation instead of a deployed system: its models describe what the investigator has proposed and observed, and its control loop monitors their evolution and adapts the investigator's context.

\section{The MORPH-FL Approach}\label{sec:approach}
\subsection{Overview}\label{sec:overview}
Figure~\ref{fig:flow} gives an overview of \tool{}. From a report and a pre-fix repository, \tool{} builds a behavior model, a structure model, and a fixed pool of candidate files. It then runs a sequence of rounds. Each round projects the current models into a request for one investigator role, asks the LLM for hypotheses and probes, grounds the proposals in the structure model, runs or reuses the probes, and assesses the results. The controller then resets the context if the progress monitor detects stagnation, and it stops when the budget or the attempt limit is exhausted. At the end, \tool{} ranks files and functions by the scores of the surviving hypotheses.

We use the following vocabulary. A \emph{hypothesis} is a candidate location together with a proposed fault mechanism and at least one \emph{prediction}, a condition that can be checked. A \emph{probe} is a planned check of a prediction, an \emph{observation} is the recorded result of running a probe, and an \emph{assessment} states whether an observation supports, contradicts, or is inconclusive for a hypothesis. An \emph{investigator role} is an LLM instruction persona with its own \emph{dialogue}, the history of its requests and responses. A \emph{context reset} clears all dialogues and prunes the hypotheses to a \emph{portfolio}. Probes, observations, and assessments together form the \emph{evidence}. Each iteration of the investigation is an \emph{attempt}, and an attempt whose LLM response is accepted is a \emph{round}. The \emph{epistemic status} of a model element records whether it was observed, derived by analysis, or conjectured. We write ``LLM'' for the language model and reserve ``model'' for the models of the investigation.

\emph{Why models.} An LLM dialogue is one undifferentiated artifact. Every fact in it is entangled with the conjecture that prompted it and the reasoning that interpreted it, so the only ways to shorten it are to truncate it or to have an LLM summarize it, and either can drop a fact or turn a conjecture into one. \tool{} instead keeps facts and conjectures as separate elements of models that conform to a metamodel. Their status cannot be confused (invariant I1 below), every observation survives a reset (I4), and every request is computed from the models, so the request after a reset is rebuilt from what was kept rather than reconstructed from what was said.

\subsection{The Investigation Metamodel}\label{sec:metamodel}
Figure~\ref{fig:metamodel} shows the metamodel, and Table~\ref{tab:models} summarizes its four models.

\emph{Behavior model.} This model holds the report together with the latest LLM interpretation of it: a trigger, the expected and the observed behavior, candidate invariants, and ambiguities. Each accepted LLM response replaces these fields rather than accumulating them. When the expected or observed behavior is missing, the model records that gap as an ambiguity. The fields are conjectures, but they give every role the same statement of the discrepancy to explain.

\emph{Structure model.} This model is a snapshot of the production Python files at the fixed revision. It stores each file's text, class and function symbols with their line ranges, and relations: imports, calls, reads, writes, and intraprocedural data flow. Every symbol and relation location carries the file's content digest. A call to a top-level definition or an explicitly imported name is marked as syntactically resolved; other calls are marked unresolved. The structure model is built once per run. It expands the candidate pool and grounds the locations that investigators propose.

\emph{Hypothesis model.} This model is the pool of live hypotheses. A hypothesis names one file and one or more locations in it, a mechanism in natural language, one or more predictions, optional causal edges, links to supporting and contradicting observations, and a score. A prediction consists of a description, a predicate, an expected value, and assumptions. A hypothesis is identified by its file, its case-folded mechanism, and the kind of probe that accompanies it; when an investigator proposes the same hypothesis again, new locations and predictions are merged into the existing element.

\emph{Evidence model.} This model holds probes, observations, and assessments. A probe names its hypothesis, the prediction it checks, a probe kind, and parameters. An observation records the probe's result, the procedure that produced it, the source location with revision and file digest, and the digest of a stored artifact. An assessment links an observation to a hypothesis with a verdict and the scope of what was observed (source presence, static structure, or execution). Observations are identified by their content and are never modified or deleted, and probes that perform the same check reuse one observation. Probe objects themselves are transient; what persists is each observation with the identifier of its probe, a cache of executed checks, and the set of probes already handled.

The operations of Section~\ref{sec:operations} maintain four invariants over these models:
\begin{IEEEdescription}[\IEEEsetlabelwidth{I4}]
\item[I1] \emph{Epistemic separation.} The status of an element is set by the operation that creates it, and no operation changes it. Observations are created only by running probes; relations only by structure extraction; behavior fields only from the report and LLM proposals; hypotheses and causal edges only from LLM proposals. Grounding marks every proposed causal edge as conjectured, whatever certainty the LLM claims, and assessment changes a hypothesis's score and links but not its status.
\item[I2] \emph{Source traceability.} Every hypothesis location and every observation carries the revision and the content digest of its file. The evidence model rejects an observation from another revision, one without procedure and digest provenance, or one whose artifact fails an integrity check, and the controller rejects an observation whose file digest differs from the structure model's.
\item[I3] \emph{Referential integrity.} Every support or contradiction link of a hypothesis resolves to a recorded observation. The links are checked against the evidence model after each assessment, and against the observations the role may access whenever the hypothesis is projected into a request.
\item[I4] \emph{Observation preservation.} No operation modifies or deletes an observation, and the evidence model rejects a changed observation under an existing identifier. A context reset leaves the set of observation identifiers unchanged, which the controller asserts at runtime, and it neither refunds nor resets the budget.
\end{IEEEdescription}
The metamodel is implemented as Python dataclasses rather than in a modeling framework such as EMF. I2--I4 are enforced by explicit checks in the evidence model, the operations, and the controller; I1 holds by construction, because no operation assigns a status after creation and grounding overwrites the status of every proposed causal edge (Appendix~\ref{app:realization}).

\emph{Extraction.} \textsc{ExtractStructure} parses every production Python file with Python's \code{ast} module, skipping test directories and test files. Files that fail to parse remain retrievable but contribute only a diagnostic.

\emph{Candidate preparation.} \tool{} ranks all files against the report with BM25, a term-based retrieval function. The five highest-ranked files seed \textsc{Expand}, which collects files reachable within two hops in either direction over relations not marked unresolved. Data-flow relations stay within a file, so in practice the neighborhood follows imports and calls. The candidate pool consists of the seeds, then the neighborhood files in BM25 order, then the remaining files in BM25 order, truncated to 20 files. The pool is fixed for the run. In a larger version of the running example, the import and call from \code{handle} to \code{normalize} would bring \code{config.py} into the pool even if BM25 ranked it below the seeds. Only pool files are ever shown to the investigator, so the pool bounds which files can receive hypotheses.

\emph{Grounding and planning.} \tool{} considers the first four proposals of a response, each with a file, a mechanism, a prediction, and a probe. \textsc{Ground} accepts a proposal only if its file was shown in the request, the proposed line exists in that file, the probe targets the same file, and the mechanism and prediction are nonempty. It then builds a source location with the revision, the file digest, and the narrowest enclosing symbol, and it adds the hypothesis to the pool or merges it with an existing one. \textsc{Plan} turns the investigator's probe specification into a typed probe of one of five kinds: a source quote, an AST query, a test, a trace, or a counterfactual comparison of two procedures. The investigator, not \tool{}, chooses the check. \tool{} checks the probe kind when planning and the kind-specific parameters when running the probe; a hypothesis whose probe proves malformed stays in the pool with score zero. \tool{} never synthesizes tests from a mechanism.

\emph{Running probes.} A source-quote probe checks whether a quoted text occurs on a given line. An AST query checks whether the file contains a node of an allowed type, such as a \code{return} statement, whose source text contains a given string; the whole file is searched. Tests, traces, and counterfactuals run only as procedures registered by the experimenter in an isolated container; an unregistered request is recorded as a blocked observation. A check, identified by probe kind, file, and parameters, executes at most once per run: a cache lets a second hypothesis that proposes the same check reuse the recorded observation, which then does not count as a new observation. A probe already handled for its hypothesis, with the same kind and parameters, is skipped entirely.

\emph{Assessment.} \textsc{Assess} reads the observed value that the prediction's predicate refers to---for an AST query, whether any node matched---and compares it with the expected value. Equal values support the prediction, unequal values contradict it, and a missing value, a blocked or timed-out procedure, or a predicate that does not fit the probe kind is inconclusive. A hypothesis's score is the signed sum of the weights of its assessments,
\begin{equation}\label{eq:score}
\mathrm{score}(h)=\sum_{e\in\mathrm{Sup}(h)} w(h,e)-\sum_{e\in\mathrm{Con}(h)} w(h,e),
\end{equation}
where $\mathrm{Sup}(h)$ and $\mathrm{Con}(h)$ are the supporting and contradicting observations, and $w(h,e)$ is 0.25 when $e$ was assessed for $h$ against a source-presence prediction, 1 for a structural prediction checked by an AST query, and 2 for a prediction checked by execution. The weights encode the relative strength of the three kinds of check; they are chosen ordering priorities, not probabilities. An additive score is the simplest aggregate in which contradictions offset support, and it treats observations as independent, a simplification we return to in Section~\ref{sec:discussion}. Each hypothesis--observation pair contributes to the score at most once.

\emph{Projection.} \textsc{Project} builds the request view from the behavior model, the current portfolio, the observations accessible to the role, and the remaining token budget. Each hypothesis appears with its locations, its mechanism labeled as unverified, its predictions, its conjectured causal edges, and the identifiers of its supporting observations, split into static and execution-based, and of its contradicting observations. Predictions of hypotheses without execution support are listed as unresolved. The view lists hypotheses in portfolio order and shows no scores.

The controller adds numbered excerpts of up to four pool files, their BM25 ranks, and up to twelve structural relations from those files. The first request shows the four leading candidates; later requests show the BM25 leader and the file of the first portfolio hypothesis and rotate through the rest of the pool. The role's dialogue, if any, precedes the new request. Because projection runs before every request, a reset needs no separate reconstruction step.

\subsection{The Investigation Loop}\label{sec:procedure}
Algorithm~\ref{alg:controller} gives the loop that ties the operations together. Lines~\ref{alg:prep-start}--\ref{alg:prep-end} prepare the structure model, the behavior model, the BM25 ranking $L$, and the candidate pool $C$, and they initialize the hypothesis pool $H$, the evidence model $E$ (including the probe cache and the set of handled probes), the role dialogues $A$, and the progress window $\Omega$.

\algtext*{EndIf}\algtext*{EndFor}
\begin{algorithm}[t]
\caption{The \tool{} investigation loop}\label{alg:controller}
\begin{algorithmic}[1]\small
\Require report $r$; repository $R$ at revision $v$; attempt limit $N$; budget $B$; portfolio bound $m$
\Ensure ranked files and functions; evidence model $E$
\State $s\gets\textsc{ExtractStructure}(R,v)$\label{alg:prep-start}
\State $b\gets\textsc{ExtractBehavior}(r,\varnothing)$
\State $L\gets\textsc{BM25}(r,s)$;\; $C\gets\textsc{Pool}(L,\textsc{Expand}(s,L_{1..5}))$
\State $H,E,A,\Omega\gets\varnothing$\label{alg:prep-end}
\For{$i\gets1$ \textbf{to} $N$}
  \If{$\textsc{Exhausted}(B)$}\label{alg:admit} \State \textbf{break} \EndIf
  \State $\rho\gets\textsc{Role}(i)$;\; $S\gets\textsc{Portfolio}(H,m)$\label{alg:select}
  \State $F\gets\textsc{Files}(C,L,S,i)$
  \State $x\gets\textsc{Project}(b,S,E,B)\oplus\textsc{Excerpts}(F)$\label{alg:project}
  \State $z\gets\textsc{Ask}(\rho,A_\rho,x)$ \Comment{charges tokens to $B$}\label{alg:ask}
  \If{$z=\bot$}\label{alg:reject} \State \textbf{continue} \Comment{rejected response} \EndIf
  \State $A_\rho\gets A_\rho\cdot(x,z)$;\; $b\gets\textsc{ExtractBehavior}(r,z)$\label{alg:accept}
  \State $(H,P)\gets\textsc{GroundAndPlan}(z,s,H,F)$\label{alg:ground}
  \State $(H,E)\gets\textsc{RunAndAssess}(P,H,E,B)$\label{alg:run}
  \State $\Omega\gets\textsc{Record}(\Omega,H,E,P,B)$\label{alg:record}
  \If{$\textsc{Stagnated}(\Omega,B)$}\label{alg:stagnated}
    \State $H\gets\textsc{Portfolio}(H,m)$;\; $A\gets\varnothing$;\; $\Omega\gets\varnothing$ \Comment{reset}\label{alg:reset}
  \EndIf
  \If{$\textsc{ExecutionStop}(H,E)$}\label{alg:stop} \State \textbf{break} \EndIf
\EndFor
\State \Return $\textsc{Rank}(L,H)$, $E$\label{alg:rank}
\end{algorithmic}
\end{algorithm}

Each iteration of the loop is one attempt. The loop ends early when the token, probe, or time budget is exhausted (line~\ref{alg:admit}); the LLM backend can also end the run when a request no longer fits the remaining budget or the context window. Roles follow a fixed schedule---behavioral, skeptical, structural, dynamic---and share the models but not their dialogues. The behavioral role separates report claims from observations, the skeptical role tries to falsify the leading hypothesis and keep a distinct alternative, the structural role traces dependencies, and the dynamic role proposes registered tests or traces and falls back to static queries.

Lines~\ref{alg:select}--\ref{alg:project} select the portfolio $S$ and the files $F$ to show and project the request; $\oplus$ appends the source excerpts to the projected view. A response that is not a well-formed object with a list of hypotheses is rejected (line~\ref{alg:reject}): it consumes the attempt and its tokens but changes no state. An accepted response is appended to the role's dialogue $A_\rho$, refreshes the behavior model, and yields the planned probes $P$ (lines~\ref{alg:accept}--\ref{alg:ground}); invalid proposals are skipped individually. Line~\ref{alg:run} runs the probes not yet handled, in the order described in Section~\ref{sec:portfolio}, and assesses their results. Line~\ref{alg:record} records the round's progress, and lines~\ref{alg:stagnated}--\ref{alg:reset} reset the context when the investigation stagnates (Section~\ref{sec:reset}). If execution procedures are registered, the run can also stop once the leading hypothesis has support from two distinct procedures, stated assumptions, and no contradiction (line~\ref{alg:stop}); the check inspects the pool as it was before any reset in the same round, and in a source-only configuration it never holds. Finally, line~\ref{alg:rank} produces the ranking (Section~\ref{sec:output}).

\subsection{The Hypothesis Portfolio}\label{sec:portfolio}
The portfolio decides which hypotheses the investigator sees. Showing every hypothesis would let near-duplicates crowd out alternatives, and showing only the leader would repeat the restart-from-best problem. \tool{} therefore selects hypotheses by score and diversity, in the spirit of maximal marginal relevance in retrieval~\cite{mmr1998}. Diversity rests on a dissimilarity between hypotheses,
\begin{equation}\label{eq:distance}
\begin{aligned}
D(h,h')={}&0.6\left(1-\frac{|\tau(h)\cap\tau(h')|}{\max(1,|\tau(h)\cup\tau(h')|)}\right)\\
&+0.4\,\mathbf{1}[\pi(h)\neq\pi(h')],
\end{aligned}
\end{equation}
where $\tau(h)$ is the set of lowercase alphabetic words of at least three letters in the mechanism of $h$ and $\pi(h)$ is its file. $D$ ranges over $[0,1]$: it combines how differently two mechanisms are worded with whether they concern different files. The portfolio $S=\textsc{Portfolio}(H,m)$ is built greedily. Starting from $S_0=\varnothing$,
\begin{equation}\label{eq:portfolio}
\begin{aligned}
S_{j+1}&=S_j\cup\{h_{j+1}\},\\
h_{j+1}&=\operatorname*{arg\,max}_{h\in H\setminus S_j}\Bigl[\mathrm{score}(h)+\min_{h'\in S_j}D(h,h')\Bigr],
\end{aligned}
\end{equation}
with the minimum over an empty set taken as 1, until $|S|=m$ or $H$ is exhausted; ties go to the higher score and then the smaller identifier. The first choice is thus the highest-scored hypothesis, and each later choice trades score against difference from those already chosen. Because $D$ is at most 1, diversity reorders only hypotheses whose scores differ by less than one, the weight of a single AST check; among those, it prefers hypotheses that differ in wording or file from the ones already chosen. The default bound is $m=3$.

Within a round, \tool{} runs every unhandled probe. It orders them by a utility that prefers inexpensive static probes, probes whose prediction contrasts with those of other hypotheses, and probes of hypotheses that differ from the rest of the pool (Appendix~\ref{app:ordering}). The order matters only when the probe or time ceiling is reached in the middle of a round.

\subsection{Stagnation Detection and Context Reset}\label{sec:reset}
After each accepted round $t$, the monitor records four quantities: the number $g_t$ of new observations that are not blocked; the fraction $u_t$ of the round's probes whose check (kind, file, and parameters) had already been executed; the pool diversity $d_t$, the mean of $D$ over all pairs of live hypotheses (zero for fewer than two); and the tokens $\kappa_t$ the round consumed. The window $\Omega$ holds the samples of the last $W$ accepted rounds since the start or the most recent reset, and $n$ counts accepted rounds since the start. The investigation has stagnated when
\begin{equation}\label{eq:reset}
\begin{aligned}
&n\ge n_0\;\wedge\;|\Omega|=W
&&\text{(ready)}\\
\wedge\;&\bar g\le\theta_g\;\wedge\;(\bar u\ge\theta_u\vee\bar d<\theta_d)
&&\text{(stalled)}\\
\wedge\;&B_{\mathrm{rem}}>\max\bigl(\kappa_0,\lfloor\kappa_t/2\rfloor\bigr)+\kappa_0
&&\text{(affordable)},
\end{aligned}
\end{equation}
where $\bar g$, $\bar u$, and $\bar d$ are window means and $B_{\mathrm{rem}}$ is the remaining token budget. The defaults are $W=3$, $n_0=4$, $\theta_g=0$, $\theta_u=\theta_d=0.5$, and a reserve of $\kappa_0=256$ tokens; Appendix~\ref{app:reset} lists two further conditions: an optional consumed-fraction gate, which is vacuous under the defaults, and a requirement that the window's rounds consumed at least $\kappa_0$ tokens, which realistic LLM rounds satisfy. With $\theta_g=0$, the gain condition requires that the last three rounds produced no new observation at all.

The conditions encode three judgments. Judging gain over a window, not a single round, avoids resetting after one unproductive response. Requiring repetition or low diversity distinguishes an investigation that circles---re-proposing executed checks or converging on similar hypotheses---from one that explores without immediate success. The budget condition requires the remaining tokens to exceed a reserve plus half the tokens of the latest round, a heuristic estimate of the cost of a fresh request; it does not guarantee that a full further round fits. The thresholds are design parameters, not calibrated values, and the evaluation varies the window size.

A reset (line~\ref{alg:reset} of Algorithm~\ref{alg:controller}) prunes the hypothesis pool to the portfolio, clears every role dialogue and the progress window, and changes nothing else. The behavior and structure models, all observations and assessments, the probe cache, the set of handled probes, the accepted-round count $n$, and the cumulative budget remain. Because the window is cleared while $n$ is kept, two resets are at least $W$ accepted rounds apart.

The effects of a reset unfold at two times. Immediately, the next request no longer carries any dialogue. Because each dialogue turn stores the full request that produced it, a long dialogue holds several stale copies of earlier state, and the reset removes them. Between resets, the dialogue is the only place where excerpts of files no longer displayed persist, since displayed files rotate, and it preserves each role's own line of reasoning; a reset trades this continuity for a request free of stale state, and the fixed-interval and no-reset variants bracket that trade-off. The visible portfolio does not change at that moment, since the portfolio of a pruned pool is the pool itself. Pruning acts later: pruned hypotheses can no longer re-enter the portfolio, no longer count toward diversity, and no longer influence the final ranking. A reset therefore forgets interpretations as well as dialogue. This forgetting is deliberate: at a stagnation point, the hypotheses outside the portfolio are those that score and diversity already rank below $m$ others, and pruning them keeps the diversity signal and the final ranking focused on the explanations the investigation is still pursuing. The \code{context_only} variant tests whether this helps. If a pruned hypothesis is proposed again, it returns with a zero score and without its former links, and its earlier probe is not rerun because it has already been handled. The observations themselves remain visible in every request (I4).

\subsection{Producing the Ranking}\label{sec:output}
When the loop ends, \textsc{Rank} orders files by the highest score of a live hypothesis in each file. A file without a live hypothesis receives score $-1$, and BM25 order breaks ties, so lexical retrieval serves as the fallback. The function ranking lists the enclosing symbols of live hypotheses' locations in decreasing order of score; it has no lexical fallback. The output also contains all observations and assessments, so each ranked location can be traced to the checks that support or contradict it. \tool{} reports no confidence value and withholds a causal claim unless some execution-based prediction in the run is supported (Appendix~\ref{app:termination}), which cannot happen in a source-only run.

\subsection{Scope and Assumptions}\label{sec:scope}
Several boundaries apply throughout. \tool{} targets Python, and its structure model is approximate: calls are resolved syntactically, dynamic dispatch stays unresolved, and the two-hop neighborhood is a heuristic, not a semantic slice. The primary evaluation uses source and AST probes only, so its assessments establish static facts; registered execution procedures are an extension outside that protocol. Scores and dissimilarities are heuristics, not probabilities. The fixed candidate pool bounds recall, and retaining every observation does not bound the size of later requests. Finally, a reset preserves observations but not the interpretations attached to pruned hypotheses. Appendix~\ref{app:implementation} documents the remaining operational details.

\section{Related Work}\label{sec:related}
We relate \tool{} to five lines of work: techniques that rank locations from fixed evidence, LLM-based localization agents, hypothesis-driven debugging, memory and context management for LLM agents, and models in fault localization and at runtime. Table~\ref{tab:closest} summarizes the approaches closest to ours in how they manage state; the descriptions concern the versions we examined.

\subsection{Ranking from Reports, Executions, and Learned Representations}
Classical fault localization ranks program elements from evidence that is fixed before ranking begins~\cite{flsurvey2016}. BugLocator combines report--source similarity with the fixes of similar past reports~\cite{buglocator2012}, and KBL improves the report used as a query by learning which keywords matter and expanding them with historical ones~\cite{kbl2025}. Execution-based techniques rank elements by their behavior in passing and failing runs: DeepRL4FL learns from coverage, statement dependencies, and code~\cite{deeprl4fl2021}, and SmartFL reasons probabilistically about the correctness of values along dynamic dependencies~\cite{smartfl2025}. LLMAO predicts faulty lines from code alone, using adapters on a pretrained code model~\cite{llmao2024}. \tool{} uses lexical retrieval to seed and order its candidate pool, to keep the BM25 leader in view, and as the fallback order for files without a live hypothesis. Its ranking is the outcome of an investigation whose state evolves, and the question we study---what that state should retain across a reset---does not arise when ranking happens once from fixed evidence. Stronger retrieval or execution evidence would complement \tool{}; the source-only configuration we evaluate does not supply the runtime evidence that execution-based methods use.

\subsection{LLM-Based Localization Agents}
AutoFL lets an LLM explore a repository with tools, explain its prediction, and aggregate predictions over repeated runs~\cite{autofl2024}. AgentFL organizes localization into comprehension, navigation, and confirmation, passing analysis results and parsed outputs between steps through a state store~\cite{agentfl2024}. Agentless narrows the search hierarchically from files to code elements to edit locations~\cite{agentless2025}. AutoCodeRover searches code through program-structure-aware interfaces before patching~\cite{autocoderover2024}, and SWE-agent gives an agent an interface designed for repository navigation and editing~\cite{sweagent2024}. RGFL generates candidate-specific reasoning to rank files and elements~\cite{rgfl2026}. LocAgent and ARISE navigate repository graphs; ARISE adds definition--use relations and token-budgeted evidence bundles~\cite{locagent2025,arise2026}. Together these systems show that LLM investigations benefit from tools, program structure, and intermediate state, so external state alone does not distinguish \tool{}. Their contributions concern how an agent navigates, reasons, and narrows the search. \tool{} addresses a complementary question: which parts of an investigation survive when its dialogue is cleared, and how checked facts stay apart from the conjectures that motivated them. Its structural neighborhood is deliberately simpler than the graphs of LocAgent or ARISE, and a richer navigation backend could feed the same controller.

\subsection{Hypothesis-Driven Debugging and Diagnosis}
Scientific debugging frames debugging as a cycle of hypothesis, prediction, experiment, and conclusion~\cite{zeller2009}. AutoSD prompts an LLM to follow this cycle, using a debugger to test its predictions and producing explanations for developers~\cite{autosd2023}. Model-based diagnosis formalizes the underlying distinction between a system description and observations~\cite{reiter1987}, and GDE maintains several candidate diagnoses against a shared set of observations while choosing the next measurement by its expected information~\cite{gde1987}. \tool{} inherits the hypothesis--prediction--observation cycle and, like GDE, keeps several candidates against one observation base. It does not offer the guarantees of model-based diagnosis: its mechanisms are natural language, its structure model is approximate, and its probe ordering is a heuristic rather than an information-theoretic choice. What it adds is a policy for keeping such a cycle productive across LLM context resets. Provenance models such as PROV-DM describe how entities derive from activities~\cite{prov2013}. \tool{} records a comparable trail for each observation---revision, file digest, procedure, and artifact digest---so that observations stay usable after the dialogue that requested them is gone.

\subsection{Memory and Context Management for LLM Agents}
Because LLMs do not use long contexts uniformly~\cite{lostmiddle2024}, agent designers manage what an agent keeps in view. MemGPT moves information between a bounded context and external storage, evicting and summarizing messages~\cite{memgpt2024}. Reflexion retains verbal reflections on feedback across trials~\cite{reflexion2023}. Ledger keeps observed source, modifications, and commands in an execution ledger, renders a current-state view, and mediates redundant actions~\cite{ledger2026}. It is the closest precedent for separating mechanically recorded state from reasoning, although its view supplements rather than replaces the interaction history. SWE-agent makes the opposite choice to ours: it collapses older observations in the agent's history while keeping its reasoning~\cite{sweagent2024}.

Memory for debugging and repair often draws on knowledge from outside the current task: MemFL supplies project summaries and debugging guidance refined on pseudo-training bugs~\cite{memfl2025}, Repository Memory retrieves historical commits, linked issues, and summaries of active files~\cite{repomem2026}, and AdaRepair-Mem selects earlier repair experiences by repair stage~\cite{adarepair2026}. Restarting is a policy of its own. In combinatorial search, randomized restarts counter heavy-tailed runtimes caused by early bad choices~\cite{restarts1998}, and recent work on automated discovery clears agent sessions while keeping the best evaluated candidate~\cite{forgetting2026}.

\tool{} differs from these policies in what it retains. It keeps observations from the current task at the target revision rather than knowledge from earlier tasks. It clears the dialogue instead of summarizing it. And it resumes from a portfolio of competing hypotheses rather than from the best candidate, because a localization score, unlike an evaluated objective, does not establish which explanation is correct. Historical memory could still inform hypothesis generation in \tool{}, provided that observations from earlier revisions remain distinguishable from checks on the target snapshot.

\subsection{Models in Fault Localization and at Runtime}\label{sec:related_mde}
MDE research has localized faults in models and in model transformations. SimFL combines statistical debugging with dynamic slicing of Simulink models, and its iterative extension refines rankings by observing additional outputs~\cite{simfl2016}. For model transformations, Burgue\~no et al. match OCL constraints to ATL rules through metamodel footprints~\cite{mtstaticfl2015}, Troya et al. apply spectrum-based localization to rule executions~\cite{mtspectrum2018}, Mu\~noz et al. combine dynamic suspiciousness with static footprints~\cite{mthybrid2022}, and SBFL-Verif obtains coverage from symbolic executions of DSLTrans transformations~\cite{mtsymbolic2024}. In all of these, the model is the artifact being debugged. In \tool{}, the models are the state of the debugger: they describe an LLM investigation of ordinary Python code. The closer lineage is therefore models@run.time, which keeps models of a running system to drive its adaptation~\cite{modelsruntime2009}, and the monitor--analyze--plan--execute loop of autonomic computing~\cite{mapek2003}; \tool{}'s monitor and reset play the role of that loop for an investigation. Work on transformation engineering emphasizes explicit source and target models, preservation obligations, and traceability~\cite{mtanalysis2017,lifting2014,mttrace2024}. \tool{} adopts these ideas in a lightweight form---typed models, a stated preservation obligation at reset, and traceable links---without a dedicated transformation language or formal verification.

\section{Evaluation}\label{sec:study}
\subsection{Study Protocol}
The evaluation separates three questions that the constructed example cannot answer: ranking effectiveness (RQ1), the contribution of context and retention policies (RQ2), and the accuracy--cost tradeoff (RQ3). All comparisons use the declared protocol and preserve failed or incomplete attempts in the coverage accounting. We distinguish the frozen experimental design, recorded execution coverage, and scored outcomes. Section~\ref{sec:results} reports the available evidence at the recorded collection cutoff; unavailable outcomes are explicitly marked rather than inferred from execution progress.

\emph{Subjects and controls.} The subjects are the pinned SWE-bench Lite and Verified splits~\cite{swebench2024}, evaluated with five pinned LLM families and three seeds. Issues shared by the splits are executed once and reported under each split's membership; the split reports are therefore not independent replications. Reference-patch changes define proxy file/function targets, while the investigator receives only the public report and pre-fix source. Prior pilot exposure must be disclosed alongside the final subject and provenance inventory.

The primary comparison includes \tool{}, continuous context, fixed-interval resets, the evidence-only control, and restricted Agentless and RGFL localization adaptations. The evidence-only control supplies observation locations and JSON results without prior dialogue or explicit hypotheses; its implementation name, \code{stateless_summary}, does not denote a generated summary. Comparisons share a 32,000-token cumulative ceiling and 16-attempt limit; the LLM's native context limit constrains an individual request separately. Deterministic retrieval controls are run once per issue. Adaptation coverage and executed workflow identities must accompany the results so restricted components are not treated as full upstream systems.

\emph{Mechanism and resource studies.} A report-blind, repository-balanced hash selection fixes 100 shared issues for the eight component controls, budget sensitivity, misleading-clue experiments, and reset-policy sensitivity. Budget curves use 16k and 48k additional runs and the matched 32k primary point. The policy track evaluates reset windows 3/4/5 with the 0.15 consumed-fraction gate enabled; comparison with the primary policy must therefore account for both the window and the gate. The misleading clue is the second BM25-ranked file; recovery eligibility and the limits of conditional comparisons are defined below.

\emph{Outcomes and inference.} Top-$k$ measures whether a proxy target appears among the first $k$ locations; mean reciprocal rank (MRR) averages the inverse rank of the first eligible target. Set measures supplement these ranking outcomes. File and function eligibility are reported separately, and seeds are averaged within each issue before repository-cluster comparisons. The declared primary file Top-1 family uses cluster sign-flip tests and Holm adjustment; repository-cluster bootstrap intervals express uncertainty. Other contrasts are descriptive, with the small number of repository clusters limiting inference. Token use, probes, and elapsed time measure actual costs rather than assuming equal ceilings imply equal expenditure.

Before any ranking contrast is interpreted, exact subject/model/seed/condition coverage and frozen source, protocol, and model identities must be checked. Smoke and incomplete results are excluded from full-study claims; interrupted and retried system costs are reported separately from completed-case metrics. Ranking contrasts address agreement with patch-derived locations, not an adjudicated causal explanation.

\subsection{Misdirection and Planned Trajectory Audits}\label{sec:audits}
Final rankings alone cannot show whether an investigator recovers from an early misleading lead or loses interpretations after pruning. The misdirection study and planned trajectory audits examine those separate questions.

The \code{initial_clue} input supplies unverified text on the first attempted request without changing retrieval or scores. The prospective misdirection track selects BM25 rank two without labels. Recovery eligibility is then checked per workflow: the clue must be wrong under reference-patch labels and its file must become the first valid-round leader. Conditional recovery percentages are descriptive because workflows can have different eligible subsets. Common-case component comparisons use matched side-study subjects and seeds.

The additional link-loss and suppression audits are planned, exploratory analyses, not outputs of the existing retention-ID summary. Recreation counts each return of a previously pruned hypothesis ID in a run/pool; a link-loss event occurs when former support/contradiction IDs are absent on return. Suppression counts validated proposal occurrences in probe-enabled shared rounds whose logical IDs are already handled when ordering begins; repeated occurrences count separately. A changed-prediction subset uses the same ID but differing predicate or expected value in ordered artifacts. Both audits report total opportunities, assessable opportunities, events, and missing/unassessable counts; percentages use assessable opportunities. Their implementation and counting version must be fixed before frequencies are interpreted.

For an eligible issue $i$ with proxy target set $G_i$, let $r_i$ be the first target's rank in the deduplicated prediction list. A missing target has $r_i=\infty$. Then
\begin{equation}
 \mathrm{Top}\mbox{-}k=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[r_i\leq k],\qquad
 \mathrm{MRR}=\frac{1}{N}\sum_{i=1}^{N}\frac{1}{r_i},
\end{equation}
where $1/\infty=0$. An empty prediction on an otherwise eligible completed execution is a miss; an issue with no eligible target is excluded from that metric and counted separately. An unexecuted or interrupted record remains missing, rather than being silently treated as a scored prediction. Recall@10 supplements first-hit measures for multi-location patches. Function outcomes require their own target inventory so that absent function labels and class-only changes do not become apparent localization failures.

The primary contrast is the within-issue, seed-averaged difference in file Top-1 between MORPH-FL and each of the five LLM comparators, separately for each model and benchmark. Effect sizes are percentage-point differences, accompanied by repository-cluster bootstrap intervals and cluster sign-flip tests. Deterministic retrieval is scored once per issue rather than multiplied by model/seed counts. A performance heatmap should encode these paired effects, with unavailable cells visibly masked; the coverage heatmap in Fig.~\ref{fig:eval-coverage} provides no such effect estimate.

\noindent\textbf{Answer to RQ1 at this cutoff.} The collection establishes deterministic-control execution coverage and partial Qwen workflow execution. It does not establish that MORPH-FL improves file or function localization over any baseline.

Completed-case costs must be accompanied by interrupted/retried expenditure, where measurable, to avoid presenting a recovery-heavy workflow as inexpensive. The tracker reports disabled Slurm accounting storage, so any unavailable attempt-level cost must remain explicit rather than reconstructed from configured limits.

For each model and benchmark, budget curves should connect only measured 16k/32k/48k points on matched issues, with uncertainty obtained from the same repository clusters used for ranking analysis. A second view should place accuracy against actual token use; its nondominated points identify policies for which no measured alternative is both cheaper and more accurate. Wall time requires within-hardware comparisons because CodeLlama and NeMo use two A30 GPUs while the other families use one. These views distinguish benefit from a larger allowance, efficiency at actual expenditure, and deployment latency.

\noindent\textbf{Answer to RQ3 at this cutoff.} Shared resource limits and the budget design are established; measured cost effectiveness, token savings, and accuracy gains from additional budget remain unknown.

\subsection{Planning Estimates and Unavailable Performance Outcomes}
The available evidence supports workload estimates, but not estimates of accuracy or baseline advantage. There are 95,282 planned execution records remaining at the cutoff. Under hypothetical sustained aggregate rates of 50, 100, or 200 records per hour, these correspond to approximately 79.4, 39.7, or 19.9 continuous days, respectively. These are conditional planning scenarios, not observed runtimes or predicted completion dates: they assume no additional retries, queue interruptions, or changes in throughput across models, workflows, and budget settings, and exclude analysis and review. They provide no estimate of Top-$k$, MRR, recovery, or retention. The companion detailed results report separates the active-study inventory, all thirty preflight measurements, historical smoke measurements, and these planning assumptions.

\section{Discussion}\label{sec:discussion}
\subsection{What the Available Results Establish}
The strongest supported conclusion concerns the boundary of the evidence. The full benchmark inventory is prepared, every model has passed its interface gate, and deterministic-control execution has a completion receipt. Primary and component execution is underway, but the collection is dominated by one model and lacks scored analysis. This supports feasibility of the experimental pipeline; it does not support a claim that selective forgetting improves fault localization. The explicit NR entries preserve that distinction and identify the outcomes still required to answer the research questions.

The coverage imbalance also explains why reporting a pooled preliminary accuracy would be difficult to interpret even if a small score subset became available. Workflow completion differs, seeds may be missing, and completed issues need not represent the full benchmark. Matched-case descriptive estimates could characterize such a subset if its subjects, exclusions, models, and seeds were disclosed, but could not stand in for the frozen full-study comparison. The overlap between Lite and Verified further prevents interpreting agreement across the two reports as two independent replications.

\subsection{Interpreting the Mechanism Comparisons}
MORPH-FL separates observation survival, productive continuation, and improved ranking at acceptable cost. Observation survival is enforced by the model invariant; the latter two require empirical evidence. A reset may remove an early conjecture from dialogue while leaving a strong but misleading hypothesis in the portfolio. It may also preserve every observation while increasing the size of subsequent requests. Thus, neither more resets nor perfect observation-ID retention is intrinsically favorable. A convincing mechanism account requires linked changes in trajectories, ranking outcomes, and resource use.

The pruning comparison is especially subtle. MORPH-FL and \code{context_only} show the same selected hypotheses immediately after a reset. They differ subsequently in whether excluded hypotheses remain available, contribute to pool diversity and later reset decisions, or appear in the final ranking. A difference between them therefore concerns these continuing consequences of pruning. Likewise, \code{no_mde} removes the projected model view from requests while preserving internal grounding, assessment, and scoring. Its effect would establish the value of the information projection under this implementation, rather than the value of every model operation in isolation. The evidence-only control represents one specific memory policy, not all possible summaries.

\subsection{Failure Modes and Practical Tradeoffs}
Retrieval bounds the attainable recall: a target outside the accessible candidate pool cannot be rescued by a better retention policy alone. File-level success can also mask poor function localization, particularly for multi-location patches. These possibilities motivate separate file/function eligibility, MRR, and recall outcomes, followed by repository-level inspection rather than a single aggregate score.

Static assessments introduce another possible failure mode. Several closely related source checks can accumulate support without establishing that the reported execution reaches the inspected code. The resulting leader may be stable and well supported under the scoring rules yet causally wrong. Portfolio diversity offers a route for preserving alternatives, but the present evidence cannot establish how often this route helps. Hypotheses recreated after pruning also lose their former interpretation links even when the underlying observations survive. The link-loss and handled-check-suppression audits are needed to distinguish successful forgetting of conjecture from loss of useful interpretation.

Resource tradeoffs can reverse a ranking-based recommendation. If continuation raises Top-1 only slightly while substantially increasing input tokens, a single-round reranker may remain preferable for a constrained deployment. If the evidence-only control matches MORPH-FL at lower expenditure, explicit hypothesis retention would need justification through recovery behavior or other measured benefits. Conversely, an accuracy gain at comparable actual cost would strengthen the case for the full policy. These are decision criteria for the pending results, not observed outcomes.

\subsection{Implications and Remaining Evidence}
The model-driven contribution makes memory operations explicit: facts, hypotheses, and dialogue have different lifetimes, and reset invariants can be inspected. Whether that separation yields a practical advantage remains an empirical question. Generalization to incident diagnosis or flaky-test triage is plausible because those tasks also accumulate observations alongside competing explanations, but it is outside this study's Python, report-based, source-only setting.

The decisive next evidence is complete, provenance-checked paired rankings, followed by matched component trajectories and actual-cost summaries. The final interpretation must accommodate improvements, null effects, and regressions across model families and repositories, disclose pilot exposure, and distinguish restricted Agentless/RGFL adaptations from their upstream systems. Until those artifacts are available, the present evaluation provides an auditable account of the study and its incomplete evidence, rather than a comparative performance claim.

\section{Threats to Validity}\label{sec:threats}
\emph{Construct validity.} Reference-patch changes are proxies for fault locations, not reviewed causal labels, and a fix can touch more than the cause of the failure. Source-only checks establish static facts rather than reproduced behavior, and class-only symbol entries must be kept distinct from function targets. The stagnation signals are proxies as well: lexical overlap of mechanism words and file identity approximate how different two explanations are, and repeated probes approximate an investigation that circles.

\emph{Internal validity.} The model-view and role variants alter the available information or the instruction schedule; they do not isolate representation format alone. Misleading-clue recovery uses workflow-specific eligible subsets rather than one randomized subset. The restricted Agentless and RGFL adaptations may cover the upstream workflows only partially. Assessment records link hypotheses to observations but not to individual predictions, which limits how finely trajectories can be interpreted.

\emph{External validity.} The study covers Python repositories in SWE-bench, two overlapping splits, and local LLMs whose outputs are nondeterministic. Public benchmark data may have been seen during LLM training, and pilot exposure to some issues must be disclosed.

\emph{Conclusion validity and reliability.} The small number of repository clusters limits statistical precision, and the policy constants are chosen rather than calibrated. Versioned manifests must keep the described implementation distinct from frozen experiment deployments, so that a result from one source version is never used to support another. Retries and interruptions can make completed-case resource summaries understate total expenditure; reporting coverage, missingness, actual costs, and version identities makes these limitations visible.

\section{Conclusion}\label{sec:conclusion}
Long LLM investigations face a choice between carrying everything forward and starting over. \tool{} replaces that choice with a selective one. It keeps the investigation in four linked models with explicit epistemic status, derives every request from those models, and, when the investigation stagnates, clears the dialogue while preserving all observations and a diverse portfolio of competing hypotheses under a cumulative budget. Invariants on the models make this forgetting precise: no conjecture becomes an observation, every observation remains traceable to the inspected revision, and no reset deletes an observation.

The evaluation design tests whether this selective forgetting improves localization, how its components contribute, and what it costs. Whatever the results, the approach shows that what an LLM investigation forgets can be specified and checked rather than left to a summarizer.

\section{Implementation Details}\label{app:implementation}
This appendix documents the operational details of the prototype that the main text summarizes. Paths are relative to \code{src/morph_fl/}.

\subsection{Realization}\label{app:realization}
The metamodel of Figure~\ref{fig:metamodel} is implemented in \code{domain/models.py}. The classes are named \code{BehavioralModel}, \code{SystemModel}, \code{Relation}, \code{SourceLocation}, \code{FaultHypothesis}, \code{Prediction}, \code{Probe}, \code{Evidence} (an observation), and \code{Assessment}; a \code{Status} enumeration holds the values observed, derived, and conjectured. Structure extraction is \code{analyze_python} in \code{program_analysis/python.py}. The other operations of Table~\ref{tab:operations} are in \code{transformations/pipeline.py}: \code{complaint_to_contract} (extract behavior), \code{compose_slice} (expand), \code{synthesize} (ground, which calls \code{hypothesis_to_probe} to plan), \code{evidence_update} (assess), and \code{fresh_context} (project). The reset combines \code{select_portfolio} with the controller's reset branch. The portfolio, ordering, and monitor policies are in \code{search/policies.py}, the loop in \code{search/controller.py}, the evidence model's insertion checks in \code{investigation/ledger.py}, and probe execution in \code{investigation/executor.py}. Dataclass annotations are not enforced at runtime, so I2--I4 rest on explicit checks, and the I4 runtime check is a Python assertion. Insertion rejects a changed observation under an existing identifier, except for the identifier of the originating probe; nested result dictionaries are not deeply immutable.

\subsection{Structure Extraction and Requests}
Structure extraction skips symbolic links, files whose names start with \code{test_}, and the directories \code{tests}, \code{test}, \code{.git}, \code{venv}, \code{.venv}, \code{__pycache__}, and \code{node_modules}. A file with a syntax error stays in the source map with a diagnostic but contributes no symbols or relations. Import relations and syntactically resolved calls are marked resolved even when their target lies outside the repository. \textsc{Expand} traverses such targets but returns only repository files, so two files that import the same external module become neighbors at the second hop.

Each excerpt holds 40 numbered lines, capped at 4,500 characters. When the report names a function of the file, the excerpt starts at that function's body, after any docstring; otherwise it is centered on a stack-trace line for the file, if the report gives one, and else on the line with the greatest identifier overlap with the report. The relations shown are the first twelve import, call, or data-flow relations, in extraction order, whose source file is displayed. A proposal's file must be displayed, but its line need only exist in the file. Requests also carry the revision, the identifiers of registered procedures, and a fixed instruction to recheck recorded contradictions and to quote numbered source.

\subsection{Grounding, Identity, and Reuse}
The proposed line defaults to 1. The enclosing symbol is the narrowest class or function whose line range contains the line, so a location inside a class but outside its methods yields a class-only entry. A prediction given as a plain string defaults to the predicate \code{source_contains} with expected value true. Hypothesis identity hashes the file, the case-folded mechanism, and the probe kind, so the same mechanism checked by two probe kinds yields two hypotheses. Logical probe identity hashes the hypothesis identity, the kind, and the parameters but not the prediction. The physical cache key is the kind, file, and parameters, and an observation's identity additionally covers the file digest, the procedure, and the result. Handled logical probes survive resets, so changing only a prediction does not cause a probe to run again. Assessment records contain the hypothesis and observation identifiers but no prediction or probe identifier; recovering the exact prediction requires the ordered proposal artifacts in the audit log.

\subsection{Probe Ordering}\label{app:ordering}
For a probe $p$ of hypothesis $h_p$, let $\alpha(p)$ count the other live hypotheses that, when $p$ was proposed, had a prediction whose predicate or expected value differs from $p$'s prediction. Probes in a round run in decreasing order of
\begin{equation}\label{eq:utility}
U(p)=\frac{q(p)\Bigl(\max\{1,\alpha(p)\}+\sum_{h'\in H\setminus\{h_p\}}D(h_p,h')\Bigr)}{\max\{10^{-3},c(p)\}},
\end{equation}
with ties broken by identifier. The reliability weight $q(p)$ is 0.9 for a source quote and 0.7 otherwise, and the estimated cost $c(p)$ is 1 for static probes and 30 for tests, traces, and counterfactuals. Both are chosen ordering parameters. Because $\alpha(p)$ is captured as proposals are processed, an earlier proposal does not count an alternative introduced later in the same response. Probes stopped by the probe or time ceiling are not marked as handled.

\subsection{Assessment Rules}
For \code{source_contains}, the observed value is the result's \code{matched} field, whatever the probe kind, and the weight is 0.25; an AST probe paired with this predicate therefore receives source-presence scope. For \code{ast_matches} on an AST query, the value is \code{matched} and the weight is 1. For \code{exit_code}, \code{test_fails}, and \code{output_contains} on a test, trace, or counterfactual, and for \code{counterfactual_changes_outcome} on a counterfactual, the value comes from the procedure's return code or output, and the weight is 2. Any other combination is inconclusive. AST matching compares against the unparsed node text, which normalizes quotes and spacing.

\subsection{Reset Conditions and Variants}\label{app:reset}
Besides the conditions of Eq.~\eqref{eq:reset}, the monitor requires that the window's token total reach the reserve $\kappa_0$ and, optionally, that the consumed budget fraction $1-B_{\mathrm{rem}}/B_{\mathrm{tot}}$ reach a threshold $\phi$. With the default $\phi=0$, the second condition always holds. The repetition fraction $u_t$ divides by the number of the round's validly grounded probes, and duplicates within one response do not count against each other. The fixed-reset variant resets after every third attempt, provided that attempt was accepted, and applies none of the monitor's conditions.

In the independent-role configuration, each role has its own hypothesis pool, behavior model, and accessible observations, while the probe cache is shared. A reset prunes every pool and clears every dialogue. Handled-probe filtering is disabled in this configuration, one progress window collects the samples of all roles, and an observation reused from another role's check counts as new for the receiving role's progress sample.

The first yields two observations, and the next three yield none and propose only executed checks, so each recent sample is $(g_t,u_t,d_t,\kappa_t)=(0,1,1,512)$. The 16,000-token budget is the library default, separate from the study's 32,000-token ceiling.

\subsection{Termination and Output}\label{app:termination}
A new attempt requires at least 64 remaining tokens, and the probe and time ceilings are tested before each attempt and between probes. The controller does not impose a hard deadline on an LLM call. The execution-based stop requires support for the leading hypothesis from at least two distinct registered procedure identifiers, nonempty assumptions, and no contradiction. It does not filter by assessment scope, and because it inspects the pool as it was before a reset in the same round, it can fire for a hypothesis that the reset has just pruned. The output's abstention flag is cleared by any supporting execution-based assessment in the run, even for a pruned or non-leading hypothesis; the confidence field is always empty. Neither the stop nor the flag certifies the leading location. In the \code{no_probes} variant, the $j$-th proposal of a response receives the score $\max(\mathrm{score},0.01(4-j))$ for $j=0,\ldots,3$. A function ranking keeps the first occurrence of each symbol and may contain class-only entries, which exact-function scoring must keep apart from functions. Artifact digests and a hash-linked audit log provide integrity and provenance, not a proof of diagnostic correctness.

1. Introduction
    A bug report describes a failure at the point where a user encounters it. The code responsible may lie elsewhere in a
repository. A developer connects the symptom to candidate locations, proposes explanations and checks them against
source or execution evidence. Large language model (LLM) agents automate parts of this investigation: AutoFL uses
repository tools to explain localization predictions, SoapFL organizes comprehension, navigation and confirmation,
and Agentless narrows candidates before repair (Kang et al., 2024; Qin et al., 2025; Xia et al., 2025). Their practical
usefulness depends on what they establish within an inference and inspection budget.
    Context management becomes an engineering concern as calls accumulate. Dialogue mixes observed source facts,
proposed mechanisms and the reasoning connecting them. Retaining it preserves useful facts and earlier mistakes;
resetting it removes both. Long-context and multi-turn studies show that additional context can be difficult to use
reliably (Liu et al., 2024; Shi et al., 2023; Laban et al., 2026). Those findings motivate explicit state management but
do not determine which localization state an agent should see.
    We distinguish three lifetimes. An observation records a check on a fixed source revision. A hypothesis remains
conjectural even when a static check supports one of its predictions. Dialogue is the working medium in which
investigators propose and interpret them. Externalizing observations and hypotheses allows requests to expose different
views of the same state. It also makes a limitation visible that ranking accuracy alone can conceal: a workflow that
produces no usable hypotheses may still return a plausible retrieval ranking.
    We present MORPH-FL, an implementation of this separation for Python repositories. Four linked runtime models
describe reported behavior, source structure, competing hypotheses and evidence. Each request projects these models
and adds bounded source excerpts. A stagnation monitor can clear role dialogues and prune hypotheses to a score-and-
diversity portfolio while retaining every recorded observation and the cumulative budget. The design draws on models
at runtime and hypothesis-driven debugging (Blair et al., 2009; Zeller, 2009). External state is established practice; the

2. Background and Motivating Example
2.1. Report-Based Fault Localization
   The input to report-based fault localization is a bug report and a snapshot of the repository before the fix. The
output is a ranked list of source locations for a developer to inspect. We consider two granularities: files, identified by
repository-relative paths, and functions, identified by qualified names within those files. A ranking says where to look.
An explanation additionally says how an operation could cause the reported failure.

    Evidence about an explanation comes from checks of different strength. A source check establishes that a line
contains some text. An abstract syntax tree (AST) query establishes that a file contains a syntactic structure. An
execution procedure establishes what the program does for chosen inputs. We follow one convention throughout: a
check supports a hypothesis when the observed value equals the value its prediction expects, for example when a
predicted expression is present in the inspected artifact. Support from a source or AST check is therefore a static fact;
it does not show that the reported execution reached the code in question. The investigator sees the report, the pre-fix
source, and the procedures it is allowed to run. It never sees the reference patch, which the evaluation uses only to
derive target locations.

2.2. Motivating Example
    Listing 1 shows a constructed example that we use throughout the paper. A report states that setting enabled
to false still displays a feature. The handler passes the normalized option to a rendering function, which is omitted.
The fault is in normalize: the expression options.get("enabled") or True evaluates to true when the option is
false. Line numbers are counted within each file, so the defaulting return is config.py:2 and the handler’s return is
handler.py:4.
    The report describes what is displayed, so an investigator may plausibly suspect the handler first, since it passes
the option to the renderer. Two explanations then compete. The bypass hypothesis claims that the handler renders the
raw option instead of the normalized value; it predicts that the handler’s return expression mentions options. The
defaulting hypothesis claims that normalize replaces an explicit false with a default; it predicts a return expression
containing or True. Table 1 shows one AST check for each prediction. The first contradicts the bypass prediction,
and the second supports the defaulting prediction. Neither check executes the program, so the defaulting explanation
remains a hypothesis, now with structural support.
    Now suppose the investigation stalls: later rounds re-propose the same checks and learn nothing new. Restarting
with an empty context would force the investigator to rediscover both results. If only the leading explanation survived
and observations were not stored separately, the refutation could disappear from the next context. The original design
therefore preserves observations and a portfolio of competing explanations while clearing dialogue. Whether these
explanations should also appear in the next request is an empirical question. Section 3 specifies the original retention
choice.

a running system and uses it to drive the system’s adaptation (Blair et al., 2009), much as the monitor–analyze–plan–
execute loop of autonomic computing does (Kephart and Chess, 2003). MORPH-FL applies this idea to an investigation

3. The MORPH-FL Approach
    The original design addresses the motivating example with three capabilities: a record of checked facts that no reset
can erase, a set of competing explanations that survives a reset without the dialogue that produced it, and a rule for
when to reset. This section builds them in that order. It first gives an overview and a shared vocabulary (Section 3.1),
then defines the models and their invariants (Section 3.2) and the operations over them (Section 3.3). Sections 3.4–3.7
assemble the operations into the investigation loop, the portfolio, the reset policy, and the final ranking, and Section 3.8
replays the running example end to end.

3.1. Overview
     Figure 1 gives an overview of MORPH-FL. From a report and a pre-fix repository, MORPH-FL builds a behavior
model, a structure model, and a fixed pool of candidate files. It then runs a sequence of rounds. Each round projects the
current models into a request for one investigator role, asks the LLM for hypotheses and probes, grounds the proposals
in the structure model, runs or reuses the probes, and assesses the results. The controller then resets the context if
the progress monitor detects stagnation, and it stops when the budget or the attempt limit is exhausted. At the end,
MORPH-FL ranks files and functions by the scores of the surviving hypotheses.
     Because the argument of this paper turns on the difference between a fact and a conjecture, the terms below are
used in exactly one sense throughout. A hypothesis is a candidate location together with a proposed fault mechanism
and at least one prediction, a condition that can be checked. A probe is a planned check of a prediction, an observation
is the recorded result of running a probe, and an assessment states whether an observation supports, contradicts, or is
inconclusive for a hypothesis. An investigator role is an LLM instruction persona with its own dialogue, the history
of its requests and responses. A context reset clears all dialogues and prunes the hypotheses to a portfolio. Probes,
observations, and assessments together form the evidence. Each iteration of the investigation is an attempt, and an
attempt whose LLM response is accepted is a round. The epistemic status of a model element records whether it was
observed, derived by analysis, or conjectured. We write “LLM” for the language model and reserve “model” for the
models of the investigation.

    Why models. An LLM dialogue is one undifferentiated artifact. Every fact in it is entangled with the conjecture
that prompted it and the reasoning that interpreted it, and shortening it by truncation or summarization can drop facts
or blur their status. MORPH-FL instead keeps facts and conjectures as separate elements of models that conform to
a metamodel. Their declared status is kept separate by controller operations (invariant I1 below), every observation
survives a reset (I4), and every request is built from the models, so the request after a reset is rebuilt from what was
kept rather than reconstructed from what was said. Between resets, a role’s earlier turns are prepended to its projected
request; that dialogue is exactly what a reset clears.

3.2. The Investigation Metamodel
     A reset can keep facts and drop conjectures only if the investigation state says which is which. The metamodel
therefore separates the state by the kind of knowledge it holds: what the report claims, what the code contains, what
the investigator conjectures, and what checks have established. Each part becomes a model with its own element types
and lifetime, so that the retention decision of Section 2.2 can be stated per model rather than per message. Figure 2
shows the metamodel, and Table 2 summarizes its four models and what a reset does to each.
     Behavior model. This model holds the report together with the latest LLM interpretation of it: a trigger, the expected
and the observed behavior, candidate invariants, and ambiguities. Each accepted LLM response replaces the trigger
and the expected and observed behavior; in the evaluated version, ambiguities were appended rather than replaced, a
defect discussed in Section 7. When the expected or observed behavior is missing, the model records that gap as an
ambiguity. The fields are conjectures, but they give every role the same statement of the discrepancy to explain.
     Structure model. This model is a snapshot of the production Python files at the fixed revision. It stores each file’s
text, class and function symbols with their line ranges, and relations: imports, calls, reads, writes, and intraprocedural
data flow. Every symbol and relation location carries the file’s content digest. A call to a top-level definition or an
explicitly imported name is marked as syntactically resolved; other calls are marked unresolved. The structure model
is built once per run. It expands the candidate pool and grounds the locations that investigators propose.
     Hypothesis model. This model is the pool of live hypotheses. A hypothesis names one file and one or more locations
in it, a mechanism in natural language, one or more predictions, optional causal edges (conjectured links along which
the fault propagates between locations), links to supporting and contradicting observations, and a score. A prediction
consists of a description, a predicate, an expected value, and assumptions. A hypothesis is identified by its file, its
case-folded mechanism, and the kind of probe that accompanies it; when an investigator proposes the same hypothesis
again, new locations and predictions are merged into the existing element.
     Evidence model. This model holds probes, observations, and assessments. A probe names its hypothesis, the
prediction it checks, a probe kind, and parameters. An observation records the probe’s result, the procedure that
produced it, the source location with revision and file digest, and the digest of a stored artifact. An assessment links
an observation to a hypothesis with a verdict and the scope of what was observed (source presence, static structure,
or execution). Observations are identified by their content; controller operations do not modify or delete them, and
probes that perform the same check reuse one observation. Probe objects themselves are transient; what persists is
each observation with the identifier of its probe, a cache of executed checks, and the set of probes already handled.
     Separating the models is not enough on its own: an operation that turned a conjecture into an observation, lost the
revision of a checked file, or dropped an observation at a reset would silently undo the separation. We therefore state
four invariants that every operation of Section 3.3 must maintain. I1 keeps facts and conjectures apart, I2 ties every
fact to the inspected source, I3 keeps the links between them consistent, and I4 is the preservation obligation of a reset.
I1 Epistemic separation. The status of an element is set by the operation that creates it, and no operation changes it.
     Observations are created only by running probes; relations only by structure extraction; behavior fields only from
     the report and LLM proposals; hypotheses and causal edges only from LLM proposals. Grounding marks every
     proposed causal edge as conjectured, whatever certainty the LLM claims, and assessment changes a hypothesis’s
     score and links but not its status.
I2 Source traceability. Every hypothesis location and every observation carries the revision and the content digest
     of its file. The evidence model rejects an observation from another revision, one without procedure and digest
     provenance, or one whose artifact fails an integrity check, and the controller rejects an observation whose file
     digest differs from the structure model’s.

The metamodel is implemented as Python dataclasses rather than in a modeling framework such as EMF. I2–I4
are enforced by explicit checks in the evidence model, the operations, and the controller; I1 holds by construction,
because no operation assigns a status after creation and grounding overwrites the status of every proposed causal
edge (Section 4.3). These checks guard the invariants at runtime; they are not a proof. The I4 assertion, for example,
compares the observation identifiers before and after a reset. Because the reset code never touches the evidence model,
the assertion guards against future regressions rather than proving a property, and it is removed when Python runs
with optimizations (-O). Status is fixed per element type and is used to keep facts and conjectures apart in requests
and assessments, not to drive control decisions. Assessments of pruned hypotheses remain in the evidence model as
history but are no longer shown.

3.3. Model Operations
     The models change only through a fixed set of operations, and this is what lets the invariants be checked: each
operation has a declared input and output model, so it is clear which operation may create an observation, which
may only create a conjecture, and which may only select. In MDE terms, extraction operations are text-to-model
and code-to-model transformations, grounding and planning are model-to-model transformations, and projection is
a model-to-view transformation that produces the LLM request. Table 3 lists the operations that build and connect
the models. In its signatures, 𝑟 is the report, 𝑅 and 𝑣 the repository and revision, 𝑧 an accepted LLM response with
proposals 𝑧𝑗 , and 𝜓𝑗 the probe parameters of proposal 𝑗; 𝑠, 𝑏, ℎ, 𝑝, 𝑒, and 𝑎 denote a structure model, behavior model,
hypothesis, probe, observation, and assessment, and 𝐻, 𝑆, 𝐸, 𝐵, 𝐴, and Ω the hypothesis pool, portfolio, evidence
model, budget, role dialogues, and progress window.
     Extraction. E XTRACTSTRUCTURE parses every production Python file with Python’s ast module, skipping test
directories and test files. Files that fail to parse remain retrievable but contribute only a diagnostic.
     Candidate preparation. MORPH-FL ranks all files against the report with BM25, a term-based retrieval func-
tion (Robertson and Zaragoza, 2009). The five highest-ranked files seed E XPAND, which collects files reachable within
two hops in either direction over relations not marked unresolved. Data-flow relations stay within a file, so in practice
the neighborhood follows imports and calls. The candidate pool consists of the seeds, then the neighborhood files in
BM25 order, then the remaining files in BM25 order, truncated to 20 files. The pool is fixed for the run. In a larger
version of the running example, the import and call from handle to normalize would bring config.py into the pool
even if BM25 ranked it below the seeds. Only pool files are ever shown to the investigator, so the pool bounds which
files can receive hypotheses.

    Grounding and planning. MORPH-FL considers the first four proposals of a response, each with a file, a
mechanism, a prediction, and a probe. G ROUND accepts a proposal only if its file was shown in the request, the proposed
line exists in that file, the probe targets the same file, and the mechanism and prediction are nonempty. It then builds
a source location with the revision, the file digest, and the narrowest enclosing symbol, and it adds the hypothesis
to the pool or merges it with an existing one. PLAN turns the investigator’s probe specification into a typed probe of
one of five kinds: a source quote, an AST query, a test, a trace, or a counterfactual comparison of two procedures.
The investigator, not MORPH-FL, chooses the check. MORPH-FL checks the probe kind when planning and the
kind-specific parameters when running the probe; a hypothesis whose probe proves malformed stays in the pool with
score zero. MORPH-FL never synthesizes tests from a mechanism.
    Running probes. A source-quote probe checks whether a quoted text occurs on a given line. An AST query checks
whether the file contains a node of an allowed type, such as a return statement, whose source text contains a
given string; the whole file is searched. Tests, traces, and counterfactuals run only as procedures registered by the
experimenter in an isolated container; an unregistered request is recorded as a blocked observation. Two mechanisms
avoid repeated work. First, a check, identified by probe kind, file, and parameters, executes at most once per run: if
another hypothesis already ran it, the recorded observation is reused and assessed for the new hypothesis, but it does
not count as new. Second, if the same hypothesis already ran a probe with the same kind and parameters, the probe is
skipped and nothing is assessed.
    Assessment. A SSESS reads the observed value that the prediction’s predicate refers to—for an AST query, whether
any node matched—and compares it with the expected value. Equal values support the prediction, unequal values
contradict it, and a missing value, a blocked or timed-out procedure, or a predicate that does not fit the probe kind is
inconclusive. A hypothesis’s score is the signed sum of the weights of its assessments,

     Projection. PROJECT builds the request view from the behavior model, the current portfolio, the observations
accessible to the role, and the remaining token budget. Each hypothesis appears with its locations, its mechanism
labeled as unverified, its predictions, its conjectured causal edges, and the identifiers of its supporting observations,
split into static and execution-based, and of its contradicting observations. Predictions of hypotheses without execution
support are listed as unresolved. The view lists hypotheses in portfolio order and shows no scores.
     The controller adds numbered excerpts of up to four pool files, their BM25 ranks, and up to twelve structural
relations from those files. The first request shows the four leading candidates; later requests show the BM25 leader and
the file of the first portfolio hypothesis and rotate through the rest of the pool. The role’s dialogue, if any, precedes the
new request. Because projection runs before every request, a reset needs no separate reconstruction step.

3.4. The Investigation Loop
    The operations say how the models change, but not in which order or when to stop. A localization investigation
must interleave asking the LLM, checking its proposals, and deciding whether to continue, while keeping every LLM
call inside a cumulative budget and giving the reset policy a defined point at which to act. Algorithm 1 gives the
loop that ties the operations together; we describe it in line order. Lines 1–4 prepare the structure model, the behavior
model, the BM25 ranking 𝐿, and the candidate pool 𝐶, and they initialize the hypothesis pool 𝐻, the evidence model
𝐸 (including the probe cache and the set of handled probes), the role dialogues 𝐴, and the progress window Ω.
    Each iteration of the loop is one attempt. The loop ends early when the token, probe, or time budget is exhausted
(line 6); the LLM backend can also end the run when a request no longer fits the remaining budget or the context
window. Roles follow a fixed schedule—behavioral, skeptical, structural, dynamic—and share the models but not
their dialogues. The behavioral role separates report claims from observations, the skeptical role tries to falsify the
leading hypothesis and keep a distinct alternative, the structural role traces dependencies, and the dynamic role proposes
registered tests or traces and falls back to static queries.

3.6. Stagnation Detection and Context Reset
    The reset policy is designed to act when observable progress stalls; whether this intervention is worth its cost
is an empirical question. Resetting too early discards each role’s line of reasoning while it is still producing new
checks; resetting too late lets the investigation keep re-proposing the same checks and converging on near-identical
explanations, as in rounds 2–4 of the running example. The reset rule therefore watches for the observable signs of that
second situation: rounds that add no new observation while the investigation either repeats executed checks or loses
diversity among its hypotheses. After each accepted round 𝑡, the monitor records four quantities: the number 𝑔𝑡 of new
observations that are not blocked; the fraction 𝑢𝑡 of the round’s probes whose check (kind, file, and parameters) had
already been executed (zero if the round has no grounded probe); the pool diversity 𝑑𝑡 , the mean of 𝐷 over all pairs of
live hypotheses (zero for fewer than two); and the tokens 𝜅𝑡 the round consumed. The window Ω holds the samples of
the last 𝑊 accepted rounds since the start or the most recent reset, and 𝑛 counts accepted rounds since the start. The
investigation has stagnated when

study budget the default thresholds rarely trigger a reset (Section 5.3).

progress window, and changes nothing else. The behavior and structure models, all observations and assessments, the
probe cache, the set of handled probes, the accepted-round count 𝑛, and the cumulative budget remain. Because the
window is cleared while 𝑛 is kept, two resets are at least 𝑊 accepted rounds apart.

backend context window.

3.7. Producing the Ranking
    When the loop ends, R ANK orders files by the highest score of a live hypothesis in each file. A file without a live
hypothesis receives score −1, and BM25 order breaks ties, so lexical retrieval serves as the fallback. A consequence
matters for interpreting the results: a file whose hypothesis was proposed but not yet checked (score 0), or contradicted
only by a source-presence check (−0.25), still ranks above every uninvestigated file. The LLM’s proposals can therefore
reorder the BM25 list without supporting evidence; Section 5.2 reports how often the top file actually changes. The
function ranking lists the enclosing symbols of live hypotheses’ locations in decreasing order of score; it has no
lexical fallback. The output contains observations and assessments, allowing hypothesis-backed locations to be linked
to recorded checks when available. Retrieval-only entries and unchecked hypotheses have no such check support.
MORPH-FL reports no confidence value. Its abstention flag is cleared by any supporting execution-based assessment
in the run, including one for a non-leading or pruned hypothesis; the flag does not certify the leading location
(Appendix A.7). It remains set for source-only runs.

3.9. Scope and Assumptions
    Several boundaries apply throughout. MORPH-FL targets Python, and its structure model is approximate: calls
are resolved syntactically, dynamic dispatch stays unresolved, and the two-hop neighborhood is a heuristic, not a
semantic slice; because import targets outside the repository are traversed, widely imported standard-library modules
act as hubs at the second hop and can make the neighborhood broad. The stagnation monitor counts an observation
as new by its identity, which includes the probe parameters, so a slightly reworded quote counts as new evidence. The
primary evaluation uses source and AST probes only, so its assessments establish static facts; registered execution
procedures are an extension outside that protocol. Scores and dissimilarities are heuristics, not probabilities. The fixed
candidate pool bounds recall, and retaining every observation does not bound the size of later requests. Finally, a reset
preserves observations but not the interpretations attached to pruned hypotheses. Appendix A documents the remaining
operational details.

4.1. Study Design
    The evaluation answers the four research questions of Section 1:
   • RQ1 (Ranking). What file- and function-ranking outcomes do the workflows produce in the frozen Qwen
     snapshot?
   • RQ2 (Investigation behavior). How often do resets occur, and what can the available workflow contrasts
     establish about context and retention?
   • RQ3 (Resources). What completed-case token and elapsed-time tradeoffs accompany the observed outcomes?
   • RQ4 (Second-model sensitivity). How do rankings and final hypothesis availability differ in the completed

     Subjects. We use SWE-bench Lite (300 issues) (Jimenez et al., 2024) and SWE-bench Verified (500 issues) (Chowd-
hury et al., 2024). The two splits share 93 issues, which are run once and reported under both splits, so the two splits
are not independent replications. For each issue, the investigator receives the bug report and the repository before the
fix. The targets are the files and functions changed by the reference patch, which the investigator never sees. These
targets are proxies for the fault, because a patch can change more than the faulty code.
     Runs. A run is one investigation of one issue by one workflow with one LLM and one random seed. The larger
planned study includes five pinned LLM families and three seeds, which would give 707 × 6 × 5 × 3 = 63,630
primary runs over the 707 unique issues. The scored primary and pilot runs have these limits: a cumulative budget of
32,000 tokens and at most 16 attempts; a per-request context limit of 16,384 tokens constrains each individual request
separately. The BM25 and graph retrieval controls are deterministic and run once per issue.
     Workflows. The primary comparison contrasts MORPH-FL with three other context policies and two restricted
adaptations of published localization systems. Continuous context keeps every dialogue and never resets. Fixed-interval
reset clears the dialogues every third attempt instead of on stagnation. The observation-only view shows the LLM the
report and recorded observations in its memory view, alongside common instructions and source excerpts, with no
hypotheses or dialogue, and never resets (Section 4.2). The Agentless and RGFL adaptations implement the localization
stages of those systems (Xia et al., 2025; Sepidband et al., 2026) inside our harness; they are restricted components,
not reproductions of the complete upstream pipelines.

5.6. Summary of Findings
    The provisional results support five statements:
   1. With Qwen2.5-Coder-7B, MORPH-FL localizes the patched file at rank one for 43–47% of issues and within
      the top ten for 76–83%, with full-minus-continuous differences of −0.24/−0.15 pp, without an equivalence
      conclusion.
   2. The observation-only view, a different projection of the same models, ranks the patched file first 7–9 pp more
      often than MORPH-FL on both splits.
   3. With DeepSeek-Coder-6.7B, the same view is the only one that yields a nonempty final hypothesis pool on 47
      of 50 runs, against 6–7 of 50; this is an operational output measure.
   4. The adaptive reset rarely fires at this budget, providing limited exposure to reset timing and no established benefit.
   5. The workflows differ mainly in which candidate file they place first, and function localization (about 20% Top-1)
      remains much weaker than file localization.

6. Discussion
6.1. What the evidence changes about the design
    The architecture combines persistent observations, competing hypotheses and adaptive dialogue resets. These have
different evidence status. Record retention and provenance are inspectable implementation properties. Their accuracy
benefit is not isolated, because every principal workflow retains evidence. Adaptive-reset benefit is also unestablished:
resets are rare and matched trajectory studies are unavailable. Thus the contribution is an executable state-lifetime
design and exploratory evidence, rather than a validated superior reset policy.
    Observation-only was a planned control; interpreting it as preferable is post hoc. Several explanations fit its
observed outcomes. Earlier hypotheses could anchor later proposals. Compact serialization and omitted fields could
reduce prompt burden. Accepted outputs could contain more source-valid candidates. Omission of the defective
behavior field could avoid artificial request growth. Its unpruned pool could also affect ranking. The available data
do not separate these explanations. In particular, most full-view DeepSeek responses did not fail the output format:
many accepted responses simply yielded few grounded hypotheses. A corrected-runtime comparison is necessary but
will not alone isolate the other factors.
    The model architecture makes interventions explicit. Omitting hypotheses from requests while retaining them
internally is different from pruning them. Clearing dialogue is different from deleting observations. This precision
is useful for designing the next study, but does not empirically validate the representation itself. No evidence-deletion
control or independently implemented model-free agent is available here.

6.2. Implications for engineering localization tools
    An intended user receives an unverified ranked shortlist with check provenance. Static support means the code
exists or has a given structure; it does not show that it caused the reported execution. The results suggest measurement
priorities rather than universal deployment advice:

6.3. Next experiments
    First quantify duplicated ambiguities and audit the generation-to-grounding funnel on saved development traces.
Distinguish malformed responses, valid-empty lists, invalid locations, pruning and budget termination. Validate
separately versioned corrected views under matched serialization and budget. Then freeze the prompt/retention factors,
primary estimand, feasible test family and clustering procedure before inspecting independent outcomes. A favorable
rerun on these same pilot issues is development evidence.
    Repeated-reset recovery needs sufficient intervention opportunities and an explicitly wrong initial lead, not merely
more ordinary runs. Complete upstream localizers and an independent unstructured tool agent would strengthen
comparison. Human label adjudication, untouched/decontaminated subjects, all-attempt resource accounting and
developer/repair outcomes are separate extensions required for the corresponding stronger claims. Expanding the
unchanged study alone would not resolve the known confounding.


7. Threats to Validity
   Construct validity. Reference-patch changes are proxies for fault locations, not reviewed causal labels, and a fix
can touch more than the cause of the failure. Source-only checks establish static facts rather than reproduced behavior,
and class-only symbol entries must be kept distinct from function targets. Nine of the 139 Lite and eight of the 219
Verified cohort issues have no function target and are excluded from function metrics. The stagnation signals are
proxies as well: lexical overlap of mechanism words and file identity approximate how different two explanations are,
and repeated probes approximate an investigation that circles.


Babaei: Preprint submitted to Elsevier                                                                    Page 20 of 33
                                         Does forgetting help in LLM fault localization?

    Internal validity. The cohorts are the issues whose runs finished first, not a random sample of either split; if
early runs favor particular repositories or easier issues, the absolute rates, and possibly the differences, can shift as
coverage grows. The observation-only view differs from MORPH-FL in several respects at once: it omits hypotheses,
behavior fields, relations, the budget, and dialogue, and it never resets, so its advantage cannot be attributed to any
single omission. The full view also serializes the complete evidence records, including provenance fields such as file
digests and artifact paths, whereas the observation-only view shows one line per observation, so the two requests differ
in length and noise as well as in content. Finally, the observation-only view was declared as a control before the study,
and our reading of it as the preferred projection is post hoc; the results that support this reading are exploratory and need
confirmation on issues not used here. Because MORPH-FL reset in few runs, its comparison with continuous context
tests the reset policy only in a minority of runs. The identical aggregate file Top-1, Top-5 and Top-10 rates of continuous
context and fixed-interval reset call for a per-issue check that resets actually change subsequent requests. The restricted
Agentless and RGFL adaptations cover the upstream workflows only partially. Assessment records link hypotheses
to observations but not to individual predictions, which limits how finely trajectories can be interpreted. Finally, a
defect in the frozen implementation affects the views that show the behavior model: when an LLM response repeats
an unresolved ambiguity, E XTRACTB EHAVIOR appends it again, so requests of MORPH-FL, continuous context, and
fixed-interval reset can carry duplicate ambiguity messages that the observation-only view never shows. The defect
was found in a DeepSeek trace; how often it occurred in each workflow has not been measured. It may contribute
to the advantage of the observation-only view, which would make that advantage partly an artifact of a correctable
defect rather than of hypothesis projection as such. A corrected version deduplicates ambiguities and is covered by a
regression test, but it has not been rerun, and all reported results use the frozen version. A rerun of the full view with
the correction on issues not used in this paper is the most direct test of this threat.
    External validity. The primary results use one 7B LLM, and the second LLM appears only in a 50-issue, single-
seed pilot whose Qwen half overlaps the primary data. Whether the observation-only advantage holds for the other
three planned families, and for larger LLMs that may follow structured formats more reliably and use hypotheses in
the request differently, is unknown. The cohorts cover ten repositories per split, and the study covers only Python
repositories in SWE-bench. Public benchmark data may have been seen during LLM training: LLMs can name the
buggy files of SWE-bench issues from the issue text alone more often than for other repositories (Liang et al.,
2025), and some issues leak their solution (Aleithan et al., 2024). A decontaminated benchmark such as SWE-

    Conclusion validity and reliability. The intervals are repository-cluster bootstrap intervals over ten clusters per split,
computed on an incomplete snapshot that has been inspected more than once, and they are not adjusted for multiplicity.

Validation history. On 28 October, synthetic regression checks exposed identity-validation gaps in model revision,

8.1. Ranking from Reports, Executions, and Learned Representations
    Most classical fault localization techniques rank program elements from evidence that is fixed before ranking
begins (Wong et al., 2016; Chang et al., 2025); spectrum-based formulas such as Tarantula and Ochiai, for example,
score statements by their coverage in passing and failing tests (Jones and Harrold, 2005; Abreu et al., 2007). BugLocator
combines report–source similarity with the fixes of similar past reports (Zhou et al., 2012), and KBL improves the
report used as a query by learning which keywords matter and expanding them with historical ones (Cai et al.,
2025). Execution-based techniques rank elements by their behavior in passing and failing runs: DeepRL4FL learns
from coverage, statement dependencies, and code (Li et al., 2021), and SmartFL reasons probabilistically about the
correctness of values along dynamic dependencies (Wu et al., 2025). LLMAO predicts faulty lines from code alone,
using adapters on a pretrained code language model (Yang et al., 2024a), and SweRank trains a retrieve-and-rerank
model that ranks code for an issue description in one pass (Reddy et al., 2026). MORPH-FL uses lexical retrieval to
seed and order its candidate pool, to keep the BM25 leader in view, and as the fallback order for files without a live
hypothesis. Its ranking is the outcome of an investigation whose state evolves, and the question we study—what that
state should retain across a reset—does not arise when ranking happens once from fixed evidence. Stronger retrieval
or execution evidence would complement MORPH-FL; the source-only configuration we evaluate does not supply the
runtime evidence that execution-based methods use.

8.2. LLM-Based Localization Agents
    AutoFL lets an LLM explore a repository with tools, explain its prediction, and aggregate predictions over repeated
runs (Kang et al., 2024). SoapFL (first released as AgentFL) organizes localization as a standard operating procedure
of comprehension, navigation, and confirmation, passing analysis results between steps through a state store (Qin
et al., 2025), and FlexFL narrows candidates in two stages with open-source LLMs and agent tools, drawing on
bug reports and tests (Xu et al., 2025a). LLM4FL divides a large code base among several agents and refines their
rankings by reflection (Rafi et al., 2024). Agentless narrows the search hierarchically from files to code elements to
edit locations (Xia et al., 2025). AutoCodeRover searches code through program-structure-aware interfaces before
patching (Zhang et al., 2024), and SWE-agent, OpenHands, and CodeAct give agents interfaces or executable actions
for repository navigation and editing (Yang et al., 2024b; Wang et al., 2025, 2024); MASAI splits the work among
sub-agents with separate contexts, one of which localizes edits (Arora et al., 2024). RGFL generates candidate-specific
reasoning to rank files and elements (Sepidband et al., 2026). LocAgent, CoSIL, and ARISE navigate repository graphs;
ARISE adds definition–use relations and token-budgeted evidence bundles (Chen et al., 2025; Jiang et al., 2025; Seddik
et al., 2026). OrcaLoca is the closest of these in managing what the agent sees: it schedules actions by priority and
prunes context by code distance (Yu et al., 2025), whereas MORPH-FL partitions context by epistemic status and
resets it on stagnation. Together these systems show that LLM investigations benefit from tools, program structure,
and intermediate state, so external state alone does not distinguish MORPH-FL. Their contributions concern how an
agent navigates, reasons, and narrows the search. MORPH-FL addresses a complementary question: which parts of an
investigation survive when its dialogue is cleared, and how checked facts stay apart from the conjectures that motivated
them. Its structural neighborhood is deliberately simpler than the graphs of LocAgent or ARISE, and a richer navigation
backend could feed the same controller.

8.3. Hypothesis-Driven Debugging and Diagnosis
    Scientific debugging frames debugging as a cycle of hypothesis, prediction, experiment, and conclusion (Zeller,
2009). AutoSD prompts an LLM to follow this cycle, using a debugger to test its predictions and producing explanations
for developers (Kang et al., 2025), and RepairAgent guides hypothesis-driven repair with a finite-state machine over
tool use (Bouzenia et al., 2025); both keep the dialogue history as their state. Model-based diagnosis formalizes the
underlying distinction between a system description and observations (Reiter, 1987), and GDE maintains several
candidate diagnoses against a shared set of observations while choosing the next measurement by its expected
information (de Kleer and Williams, 1987). MORPH-FL inherits the hypothesis–prediction–observation cycle and, like
GDE, keeps several candidates against one observation base. It does not offer the guarantees of model-based diagnosis:
its mechanisms are natural language, its structure model is approximate, and its probe ordering is a heuristic rather
than an information-theoretic choice. It adds an explicit retention/reset policy to that cycle; its productivity benefit

remains unestablished. Keeping several candidate explanations consistent with a shared, growing set of facts also recalls
blackboard architectures such as Hearsay-II, in which independent knowledge sources post and revise hypotheses on
a shared store (Erman et al., 1980), and assumption-based truth maintenance, which records the assumptions under
which each conclusion holds (de Kleer, 1986). MORPH-FL’s roles play the part of knowledge sources over a shared
evidence model, without the formal dependency tracking of an ATMS. Provenance models such as PROV-DM describe
how entities derive from activities (Moreau and Missier, 2013). MORPH-FL records a comparable trail for each
observation—revision, file digest, procedure, and artifact digest—so that observations stay usable after the dialogue
that requested them is gone.

8.4. Memory and Context Management for LLM Agents
     Because LLMs do not use long contexts uniformly (Liu et al., 2024; Hong et al., 2025), agent designers manage what
an agent keeps in view. Prompt compression removes tokens that an LLM can do without (Jiang et al., 2023). MemGPT
moves information between a bounded context and external storage, evicting and summarizing messages (Packer et al.,
2023), and ACON learns natural-language guidelines for compressing an agent’s history and observations (Kang et al.,
2026). Generative Agents, MemoryBank, and A-Mem keep long-term memory stores that agents retrieve from and
reflect on (Park et al., 2023; Zhong et al., 2024; Xu et al., 2025b). Reflexion retains verbal reflections on feedback across
trials (Shinn et al., 2023). Ledger keeps observed source, modifications, and commands in an execution ledger, renders
a current-state view, and mediates redundant actions (Wang et al., 2026b). It is the closest precedent for separating
mechanically recorded state from reasoning, although its view supplements rather than replaces the interaction history.
SWE-agent makes the opposite choice to ours: it collapses older observations in the agent’s history while keeping its
reasoning (Yang et al., 2024b). Lindenbauer et al. find that such observation masking matches LLM summarization on
SWE-bench at about half the cost (Lindenbauer et al., 2025), and HiAgent keeps full action–observation pairs only for
the current subgoal while summarizing completed ones (Hu et al., 2025). MORPH-FL’s observation-only view inverts
the choice, keeping every observation and dropping the reasoning, but the bundled contrast and known defect prevent
attributing the observed advantage to that inversion.
     Memory for debugging and repair often draws on knowledge from outside the current task: MemFL supplies
project summaries and debugging guidance refined on pseudo-training bugs (Yeo et al., 2025), Repository Memory
retrieves historical commits, linked issues, and summaries of active files (Wang et al., 2026a), and AdaRepair-Mem
selects earlier repair experiences with coverage-, quality-, and stage-aware criteria (Luo et al., 2026). Restarting is
a policy of its own. In combinatorial search, randomized restarts counter heavy-tailed runtimes caused by early bad
choices (Gomes et al., 1998), and recent work on automated discovery clears agent sessions while keeping the best
evaluated candidate (Tan et al., 2026).
     MORPH-FL differs from these policies in what it retains. It keeps observations from the current task at the target
revision rather than knowledge from earlier tasks. It clears the dialogue instead of summarizing it. And it resumes
from a portfolio of competing hypotheses rather than from the best candidate, because a localization score, unlike an
evaluated objective, does not establish which explanation is correct. Historical memory could still inform hypothesis
generation in MORPH-FL, provided that observations from earlier revisions remain distinguishable from checks on
the target snapshot.

8.5. Models in Fault Localization and at Runtime
    MDE research has localized faults in Simulink models and model transformations (Liu et al., 2016; Troya et al.,
2018). In those settings the model is the artifact being debugged. Here the models describe an investigator of ordinary
Python code. The closer lineage is models@run.time, which keeps explicit models to monitor and adapt a running
system (Blair et al., 2009), and the monitor–analyze–plan–execute loop of autonomic computing (Kephart and Chess,
2003). MORPH-FL applies that pattern to investigation state and context. Its lightweight dataclasses, explicit checks
and source links provide operational traceability without a dedicated transformation language or formal proof. Their
value as a representation is not isolated by the available comparisons.

et al., 2026). These are relevant connections to prompt sensitivity and explicit hypotheses, but their task differs from

9. Conclusion
     MORPH-FL separates a localization investigation into runtime models of behavior, structure, hypotheses and
evidence, allowing context to be rebuilt without relying on dialogue as its sole memory. Its implemented reset retains
observations and a selected hypothesis portfolio under a cumulative budget. These properties specify what the system
keeps; they do not establish a benefit from keeping or resetting it.
     In the frozen Qwen snapshot the full workflow obtains file Top-1 of 42.93% and 46.58%, with small observed
differences from continuous and fixed-reset workflows. Observation-only reaches 50.36% and 55.56%. In the complete
pilot it yields final hypotheses on 47/50 DeepSeek issues versus 6–7/50 under richer views, while all four retain 40%
file Top-1 and observation-only takes longer. File accuracy can therefore conceal failed investigation behind retrieval
fallback. Bundled prompt changes, a known prompt-growth defect, completion-selected cohorts and source-only patch
proxies prevent stronger causal or deployment claims. Corrected, factor-isolating comparisons on independent subjects
are needed before recommending a context policy.


A. Implementation Details
    This appendix documents the operational details of the prototype that the main text summarizes. Paths are relative
to src/morph_fl/.

A.1. Realization
    Section 4.3 maps the algorithm to the code. Two details complete it. The ledger rejects a changed observation
under an existing identifier, except for the identifier of the originating probe, and nested result dictionaries are not
deeply immutable. The reset itself combines select_portfolio with the controller’s reset branch, which clears the
role sessions and the monitor window.

A.2. Structure Extraction and Requests
     Structure extraction skips symbolic links, files whose names start with test_, and the directories tests, test,
.git, venv, .venv, __pycache__, and node_modules. A file with a syntax error stays in the source map with a
diagnostic but contributes no symbols or relations. Import relations and syntactically resolved calls are marked resolved
even when their target lies outside the repository. E XPAND traverses such targets but returns only repository files, so
two files that import the same external module become neighbors at the second hop.
     Each excerpt holds 40 numbered lines, capped at 4,500 characters. When the report names a function of the file,
the excerpt starts at that function’s body, after any docstring; otherwise it is centered on a stack-trace line for the file,
if the report gives one, and else on the line with the greatest identifier overlap with the report. The relations shown are
the first twelve import, call, or data-flow relations, in extraction order, whose source file is displayed. A proposal’s file
must be displayed, but its line need only exist in the file. Requests also carry the revision, the identifiers of registered
procedures, and a fixed instruction to recheck recorded contradictions and to quote numbered source.

A.3. Grounding, Identity, and Reuse
    The proposed line defaults to 1. The enclosing symbol is the narrowest class or function whose line range contains
the line, so a location inside a class but outside its methods yields a class-only entry. A prediction given as a plain
string defaults to the predicate source_contains with expected value true. Hypothesis identity hashes the file,
the case-folded mechanism, and the probe kind, so the same mechanism checked by two probe kinds yields two
hypotheses. Logical probe identity hashes the hypothesis identity, the kind, and the parameters but not the prediction.
The physical cache key is the kind, file, and parameters, and an observation’s identity additionally covers the file digest,
the procedure, and the result. Handled logical probes survive resets, so changing only a prediction does not cause a
probe to run again. Assessment records contain the hypothesis and observation identifiers but no prediction or probe
identifier; recovering the exact prediction requires the ordered proposal artifacts in the audit log.

    For source_contains, the observed value is the result’s matched field, whatever the probe kind, and the weight

against the unparsed node text, which normalizes quotes and spacing.

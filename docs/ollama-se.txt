# Categorized Ollama models for Software Engineering, with BibTeX references

I would organize the models along two independent dimensions: architecture/model family and software engineering capability. This avoids treating every coding model as interchangeable and makes it easier to select baselines for experiments.

The bibliography below distinguishes original model papers from software engineering evaluation papers. One correction to my previous response: the earlier broad paper titles should be treated as search leads, not verified citations. I will not attribute a paper to ICSE, IEEE TSE, or EMSE without sufficient bibliographic confidence.

## 1. Model taxonomy by architecture and specialization

Model families and suggested Ollama tags; exact tag availability should be checked against your installed Ollama registry.

| Category                             | Models                        | Main specialization                    | Best SE applications                                |
| ------------------------------------ | ----------------------------- | -------------------------------------- | --------------------------------------------------- |
| General-purpose code LLMs            | Qwen2.5-Coder, DeepSeek-Coder | Code generation and reasoning          | Code comprehension, repair, refactoring             |
| Mixture-of-Experts (MoE) code models | DeepSeek-Coder-V2             | Sparse expert-based computation        | Complex code tasks, large-scale code reasoning      |
| Agent-oriented coding models         | Devstral                      | Repository work and tool-driven coding | Multi-file changes, issue resolution                |
| Code completion / infilling models   | StarCoder2, Code Llama        | Code continuation and infilling        | IDE assistance, code completion                     |
| Enterprise-oriented code models      | Granite Code                  | Code generation and understanding      | Maintenance, code explanation, controlled baselines |

These categories are not mutually exclusive. For example, DeepSeek-Coder-V2 is both code-specialized and MoE-based, while Devstral is best distinguished by its agentic coding focus rather than treated as a separate architectural family.

## 2. Categorization by SE expertise

### A. Code understanding, generation and refactoring

Primary candidates: Qwen2.5-Coder, DeepSeek-Coder, Granite Code

Typical tasks

* Explain functions and classes

* Identify design problems and code smells

* Generate implementations and refactor code

* Analyze dependencies and changes

Suggested evaluation: compilation success, functional correctness, design-constraint satisfaction and behavior preservation.

### B. Automated program repair

Primary candidates: Qwen2.5-Coder, DeepSeek-Coder-V2, Devstral

Typical tasks

* Repair bugs from issue descriptions

* Localize faulty code

* Generate and validate patches

* Resolve repository-level issues

Suggested evaluation: plausible patches, independently validated correctness, regression tests and resolved issues.

### C. Testing and test generation

Primary candidates: Qwen2.5-Coder, DeepSeek-Coder, StarCoder2

Typical tasks

* Generate unit tests

* Generate boundary and negative test cases

* Repair failing tests

* Improve mutation coverage

Suggested evaluation: compilability, branch coverage, mutation score and fault-detection effectiveness.

### D. Agentic and repository-level software engineering

Primary candidates: Devstral, Qwen2.5-Coder, DeepSeek-Coder-V2

Typical tasks

* Execute issue-to-patch workflows

* Navigate repositories and use development tools

* Coordinate planning, implementation and testing

* Recover from failed tool calls

Suggested evaluation: task resolution rate, tool-use accuracy, execution cost, latency and reproducibility.

### E. Code completion and historical baselines

Primary candidates: StarCoder2, Code Llama, Qwen2.5-Coder

Typical tasks

* Fill in missing code

* Complete functions from context

* Predict code tokens

* Compare newer models with established baselines

Suggested evaluation: pass@k, exact match where appropriate, compilation rate and latency.

## 5. How to build a venue-specific bibliography for ICSE, TSE and EMSE

For a defensible related-work section, I recommend separating the literature into three evidence groups:

| Evidence group          | What to cite                                                        | What it supports                                               |
| ----------------------- | ------------------------------------------------------------------- | -------------------------------------------------------------- |
| Model architecture      | Qwen, DeepSeek, StarCoder2, Code Llama and Granite technical papers | Architecture, training and model capabilities                  |
| SE task evaluation      | ICSE studies on testing and repair; TSE and EMSE empirical studies  | Task-specific evaluation methods and findings                  |
| Repository-level agents | SWE-bench and studies of tool-using coding agents                   | Issue resolution, tool use and realistic repository evaluation |

Use these targeted searches to identify the exact peer-reviewed venue records before generating the final `.bib` file:

* [ICSE: code LLMs, automated repair and testing](https://scholar.google.com/scholar?q=ICSE+large+language+models+code+repair+test+generation)

* [IEEE TSE: empirical studies of LLMs for software engineering](https://scholar.google.com/scholar?q=IEEE+Transactions+on+Software+Engineering+LLM+code+generation+repair)

* [EMSE: empirical evaluation of LLM-based software development](https://scholar.google.com/scholar?q=Empirical+Software+Engineering+LLM+software+engineering+empirical+study)



## Verified selection for the prospective MORPH-FL Nibi evaluation (2026-10-19)

The executable four-checkpoint selection and primary study links are recorded in `experiments/full/models.md`; pinned HF revisions are in `experiments/full/pins.json`. Nibi uses BF16 instruction checkpoints, not these Ollama quantization tags. Qwen2.5-Coder 7B/32B and Qwen3-Coder 30B-A3B provide current/pilot-continuity configurations; DeepSeek-Coder 6.7B-Instruct is an ICSE-used historical cross-family control. Venue evidence supports prior use, not universal superiority or comparable measured performance. No unverified TSE citation is claimed.

2026-10-20 five-family evaluation revision
-----------------------------------------
The active prospective Nibi evaluation replaces the three Qwen variants with five distinct families: Qwen2.5-Coder-7B-Instruct; DeepSeek-Coder-6.7B-Instruct; CodeLlama-7B-Instruct-hf; Mistral-Nemo-Instruct-2407; IBM Granite-3.1-8B-Instruct. Native BF16 checkpoints and immutable revisions, rather than Ollama quantizations, are used. COSMosFL (https://coinse.github.io/publications/pdfs/Cho2025aa.pdf, Section III-B) supplies direct localization precedent for Qwen2.5-Coder 7B, CodeLlama 7B, Mistral NeMo 12B and Granite 3.0 8B. Granite 3.1 is a disclosed successor substitution. DeepSeek evidence comes from the ICSE 2025 PInG artifact (https://github.com/NecoraNyaru/PInG), a broader SE task. This does not establish widespread localization use of all five exact checkpoints. See experiments/full/models.md and pins.json for the verified selection and limitations.
